# Требования, сценарии и критерии приёмки

Требование описывает нужный результат, а не внутреннюю реализацию. Функциональное требование говорит, что система делает; нефункциональное — с каким качеством; бизнес-правило — ограничение предметной области.

| Вид | Пример |
| --- | --- |
| Функциональное | Система показывает доступные слоты выбранного врача |
| Бизнес-правило | Нельзя отменить запись менее чем за 2 часа до начала |
| NFR | Поиск слотов отвечает не дольше 500 мс для 95% запросов |

User story полезна для обсуждения: «Как клиент, я хочу отменить запись, чтобы освободить слот». Для сложного поведения добавьте сценарий и критерии. Критерий должен быть наблюдаемым:

```text
Дано: запись начинается через 3 часа
Когда: клиент отменяет её
Тогда: статус становится cancelled, слот доступен для новой записи
И: клиент получает подтверждение отмены
```

**Антипример:** «Интерфейс должен быть удобным». Исправление: «Пользователь создаёт запись не более чем за 4 шага; при ошибке поля система показывает причину рядом с полем».

Не смешивайте требование и дизайн. «Использовать Redis» — решение; «повторный запрос доступности не должен перегружать БД» — потребность качества.
