# SQL, NoSQL и кэш

Выбирайте хранилище от формы данных и гарантий, а не от популярности. PostgreSQL подходит для записи: связи, ограничения, транзакции и запросы по расписанию важнее горизонтального масштабирования. Документное NoSQL полезно для гибких документов с редкими связями; key-value — для быстрых временных значений. NoSQL не отменяет моделирование и согласованность.

| Потребность | Выбор в кейсе | Причина |
| --- | --- | --- |
| Запись и слот | SQL/PostgreSQL | Транзакции, связи, уникальность |
| Короткий результат поиска | Redis | Быстрое чтение и TTL |
| Неизменяемый аудит | Отдельное хранилище/поток | Долгое хранение и поиск |

При **cache-aside** приложение читает Redis; при промахе читает БД, кладёт результат с TTL и возвращает его. При изменении расписания кэш соответствующего врача инвалидируют. TTL ограничивает устаревание, но не гарантирует актуальность.

Не кэшируйте «свободен ли слот» как окончательную истину: финальная проверка и ограничение должны быть в транзакции БД. Для cache stampede используйте короткую блокировку, вероятностное раннее обновление или single-flight: иначе сотни промахов одновременно ударят в БД.
