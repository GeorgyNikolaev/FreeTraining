# AS-IS и TO-BE: моделируем изменения процесса

AS-IS описывает фактический процесс, включая обходные пути. TO-BE описывает целевой процесс после изменения. Не рисуйте TO-BE, пока не понятны цель и проблема AS-IS: иначе можно автоматизировать ненужный шаг.

Для записи AS-IS может быть таким: клиент звонит → администратор смотрит календарь → записывает вручную → звонит с подтверждением. Проблемы: звонки, ошибки при параллельных запросах, нет истории.

TO-BE: клиент выбирает слот → система проверяет доступность → создаёт запись → отправляет подтверждение. У каждой границы есть владелец и вход/выход. Например, платёжный провайдер не часть нашей системы, но его результат влияет на статус записи.

Проверяйте модель вопросами: где начинается и заканчивается процесс? Кто инициирует действие? Какие данные меняются? Какие исключения меняют путь? Модель без исключений — только счастливый путь, а не спецификация.
