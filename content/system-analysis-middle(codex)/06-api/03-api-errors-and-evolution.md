# Ошибки и развитие API без поломки клиентов

Ошибка — часть контракта. Ответ должен быть машинно читаемым и полезным человеку, но не раскрывать внутренности.

```json
{
  "code": "SLOT_UNAVAILABLE",
  "message": "Выбранный слот уже недоступен",
  "traceId": "01J...",
  "details": [{"field": "slotId", "reason": "occupied"}]
}
```

Не возвращайте stack trace, SQL и секреты. `traceId` помогает поддержке найти событие в логах. Ошибка валидации — обычно `400` или `422` по принятой конвенции; важнее единообразие, чем выбор одного из двух.

Сначала предпочитайте обратимо-совместимые изменения: новое необязательное поле, новый endpoint, дополнительное значение enum с продуманным поведением старых клиентов. Удаление поля и смена его смысла ломают контракт. Версию в URL (`/v2`) используйте для действительно несовместимого набора изменений и заранее публикуйте срок поддержки старой версии.
