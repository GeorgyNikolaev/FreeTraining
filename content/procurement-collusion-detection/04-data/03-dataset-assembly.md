# Сборка датасета

XML распакован, теперь из него нужно сделать таблицы, по которым можно считать. Этот урок — про решения, которые принимаются на этом шаге и потом уже не переигрываются.

## Целевая схема

Минимальный набор — три таблицы.

| Таблица | Гранулярность | Ключевые поля |
|---|---|---|
| `purchases` | Одна строка на лот | `purchase_id`, `customer_inn`, `okpd2`, `region`, `nmck`, `method`, `etp`, `dt_bids_end`, `dt_auction`, `dt_result` |
| `bids` | Одна строка на участника в лоте | `purchase_id`, `participant_inn`, `price`, `rank`, `is_winner`, `is_rejected`, `reject_reason` |
| `contracts` | Одна строка на контракт | `purchase_id`, `contract_id`, `supplier_inn`, `contract_price`, `dt_signed`, `status` |

## Решение первое: единица наблюдения — лот

Одно извещение может содержать несколько лотов, и торг по каждому идёт отдельно: свои участники, свои цены, свой победитель. Если сделать единицей наблюдения извещение, многолотовые закупки развалят все показатели: число участников окажется суммой по лотам, а минимальная цена — минимумом по несопоставимым предметам.

Поэтому `purchase_id` — это пара «реестровый номер извещения + номер лота», даже когда лот один. Переделывать это на середине работы дорого.

## Решение второе: ИНН — строка

```python
import pandas as pd

bids = pd.read_csv(
    "bids.csv",
    dtype={"participant_inn": "string", "purchase_id": "string"},
)
```

ИНН юридического лица — 10 знаков, индивидуального предпринимателя — 12, и он может начинаться с нуля. Прочитанный как число, ИНН `0277083721` превращается в `277083721`, и участник из Башкортостана бесследно распадается на два разных. Ошибка тихая: ничего не падает, просто граф участников оказывается на несколько процентов беднее, чем должен.

То же касается `purchase_id`: 19-значный реестровый номер, прочитанный как число, теряет точность в формате с плавающей точкой.

## Решение третье: какую версию протокола брать

Протоколы пересматриваются: по предписанию контрольного органа, по решению самого заказчика. В выгрузке окажется несколько версий одного документа. Брать нужно последнюю действующую — и обязательно сохранить признак того, что пересмотр был: сам факт отмены протокола по предписанию является содержательным признаком.

```python
bids = (
    bids.sort_values(["purchase_id", "doc_version"])
        .drop_duplicates(subset=["purchase_id", "participant_inn"], keep="last")
)
```

## Решение четвёртое: что делать с несостоявшимися закупками

Закупка, на которую подана одна заявка или ни одной, состоявшейся не признаётся. Такие процедуры составляют заметную долю массива, и для них не определён ни один признак, основанный на сравнении участников.

Выбрасывать их нельзя: доля несостоявшихся закупок у конкретного заказчика — сама по себе сильный признак. Правильно — вынести их в отдельную ветку анализа и считать по ним агрегаты уровня заказчика и участника, не пытаясь считать внутрипроцедурные показатели.

## Сборка признаковой таблицы

```python
g = bids.groupby("purchase_id")
agg = g.agg(
    n_participants=("participant_inn", "nunique"),
    price_min=("price", "min"),
    price_max=("price", "max"),
    price_std=("price", "std"),
    n_rejected=("is_rejected", "sum"),
)

winner = (
    bids.loc[bids["is_winner"], ["purchase_id", "participant_inn", "price"]]
        .rename(columns={"participant_inn": "winner_inn", "price": "winner_price"})
)

df = (
    purchases
    .merge(agg, on="purchase_id", how="left")
    .merge(winner, on="purchase_id", how="left")
)

df["drop_rate"] = (df["nmck"] - df["winner_price"]) / df["nmck"]
df["gap_to_min"] = (df["winner_price"] - df["price_min"]) / df["nmck"]
```

`drop_rate` — глубина снижения победителя, `gap_to_min` — насколько цена победителя выше минимального предложения в закупке. Второй показатель в нормальной закупке равен нулю: побеждает тот, кто предложил меньше всех. Значимо положительное значение означает, что участники с более низкой ценой до контракта не дошли, — подпись, разобранная в модуле 03.

Отсюда прямое правило отбора кандидатов:

```python
cheapest = (
    bids.sort_values("price")
        .groupby("purchase_id", as_index=False)
        .first()[["purchase_id", "is_rejected"]]
        .rename(columns={"is_rejected": "cheapest_rejected"})
)

df = df.merge(cheapest, on="purchase_id", how="left")

taran_candidate = (
    df["cheapest_rejected"]
    & (df["drop_rate"] < 0.02)
    & (df["gap_to_min"] > 0.20)
    & (df["n_participants"] >= 3)
)
```

Это не модель, а правило, воспроизводящее описанную схему. Посчитайте его на своей выборке в первый же день: доля срабатываний сразу покажет, есть ли в ваших данных то, что вы собираетесь искать.

## Проверки качества

Каждую из этих проверок стоит выполнить один раз и записать результат в дипломе — это раздел о качестве данных, который обычно приходится придумывать в последний момент.

| Проверка | Что означает нарушение |
|---|---|
| Число строк в `bids` совпадает с числом участников из протокола | Потеряны участники при разборе XML |
| `winner_price <= nmck` | Ошибка разбора цены или неверный лот |
| Ровно один `is_winner` на лот | Взяты разные версии протокола |
| `dt_bids_end <= dt_auction <= dt_result` | Перепутаны даты из разных документов |
| Ранги идут подряд без пропусков | Часть участников не попала в выгрузку |
| Доля закупок без протокола итогов | Незавершённые или отменённые процедуры |
| Распределение числа документов по дням без провалов | Неполная выгрузка |

## Где ошибаются

**Соединяют `bids` и `contracts` напрямую по ИНН.** Один и тот же поставщик исполняет сотни контрактов; соединение без `purchase_id` порождает декартово произведение, и таблица распухает в тысячи раз. Ключ соединения — закупка, ИНН только дополняет.

**Считают цену победителя из реестра контрактов.** Цена контракта может измениться при исполнении. Для анализа торга нужна цена из протокола подведения итогов; цена контракта — отдельный признак с другим смыслом.

**Нормализуют наименования участников вместо использования ИНН.** Соблазн понятен: наименования выглядят читаемее. Но «ООО "СтройМонтаж"» в регионе может быть три, а одно юридическое лицо за три года сменит название дважды. ИНН — единственный корректный ключ, наименование хранится только для отчётов.
