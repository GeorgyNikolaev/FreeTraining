# Свои события и событийный стриминг

Режимы из прошлого урока показывают то, что видит движок: шаги, обновления, токены. Но самое понятное для студента сообщение — «проверяю признак 3 из 5» — движку неизвестно. Его отправляет сам узел.

## `get_stream_writer`

```python
from langgraph.config import get_stream_writer


def check_criterion(task: CriterionTask) -> dict:
    writer = get_stream_writer()
    writer({"этап": "проверяю признак", "текст": task["criterion"]})

    verdict = checker.invoke(...)

    writer({"этап": "признак проверен", "результат": verdict.passed})
    return {"checks": [...]}
```

Всё, что передано в `writer`, приходит подписчику в режиме `custom`:

```
stream_mode="custom"
  {'этап': 'проверяю признак', 'текст': 'Веер отправляет по одному Send на признак'}
```

Функция доступна и в узлах, и в инструментах (у `ToolRuntime` есть `stream_writer`). Для инструментов это особенно ценно: поиск по урокам идёт секунду-две, и сообщить «ищу» может только он сам.

Три правила, чтобы эти события были полезны:

- **Структура, а не строка.** `{"этап": ..., "деталь": ...}` разложится в интерфейсе; «Проверяю признак 3 из 5…» придётся разбирать регулярным выражением.
- **Только то, что можно показать.** События уходят клиенту — внутренним отладочным данным там не место.
- **Без тайны.** Промпты, идентификаторы чужих записей, куски контекста в события не кладут.

## Что делать с прерываниями в потоке

Когда узел зовёт `interrupt`, поток не обрывается ошибкой: событие прерывания приходит наравне с остальными, а сам поток завершается. Клиенту надо отличить «ответ дописан» от «жду ответа человека» — иначе интерфейс покажет пустоту.

Практический приём: после окончания потока всегда смотреть снимок состояния. Непустые `snapshot.interrupts` означают «показать вопрос», пустые и `next == ()` — «всё, ответ готов».

## Событийный стриминг: протокол на блоках содержимого

В langgraph 1.2 появился новый способ читать поток — `astream_events(..., version="v3")`. На сентябрь 2026 он помечен как экспериментальный (`LangChainBetaWarning`), и в продакшен-коде я бы пока держал обычные режимы. Но знать о нём стоит: именно туда движется API.

Идея в том, что вместо одного потока разнородных событий вы получаете объект прогона с **типизированными проекциями**, каждую из которых читаете отдельно:

```python
run = await graph.astream_events(payload, config, version="v3")

async for call_stream in run.messages:        # по одному потоку на вызов модели
    async for part in call_stream:
        print(part)
```

Проекции у объекта прогона: `values`, `messages`, `lifecycle`, `subgraphs`, `interrupts`, `interrupted`, `output`, плюс `abort` для остановки.

А вот что приходит внутри `run.messages` (настоящий вывод, langgraph 1.2.11):

```
{'event': 'message-start', 'role': 'ai', 'id': 'lc_run--01a0bfef…'}
{'event': 'content-block-start', 'index': 0, 'content': {'type': 'text', 'text': ''}}
{'event': 'content-block-delta', 'index': 0, 'delta': {'type': 'text-delta', 'text': 'Редьюсер'}}
{'event': 'content-block-delta', 'index': 0, 'delta': {'type': 'text-delta', 'text': ' объединяет'}}
{'event': 'content-block-finish', 'index': 0, 'content': {'type': 'text', 'text': 'Редьюсер объединяет значения.'}}
{'event': 'message-finish'}
```

Это и есть «протокол на блоках содержимого»: у ответа модели могут быть разные блоки — текст, рассуждение, вызов инструмента, — и каждый имеет собственные события начала, приращения и конца. Разбирать такой поток удобнее, чем склеивать текст из токенов: клиент понимает, к какому блоку относится фрагмент, и может, например, показывать вызовы инструментов отдельным элементом.

Старые версии (`v1`, `v2`) и обычные `stream_mode` никуда не делись и продолжают работать.

Одно известное ограничение: смешивать уровни нельзя. Если внешний прогон идёт на `v3`, а внутри узла вызывается `stream(stream_mode="messages")` старого образца, токены внутреннего вызова наружу не попадут — придёт только финальное сообщение.

## Как выбрать

| Задача | Чем делать |
|---|---|
| Показать ответ по мере печати | `stream_mode="messages"` с фильтром по узлу |
| Показать, чем агент занят | свои события через `get_stream_writer` |
| Обновлять состояние интерфейса по шагам | `stream_mode="updates"` |
| Разобрать ответ по блокам: текст, вызовы инструментов, рассуждение | `astream_events(version="v3")`, с оглядкой на статус беты |

## Типичные ошибки

**Свои события вместо состояния.** Событие — это уведомление, оно нигде не сохраняется. Если факт нужен после перезапуска, он должен попасть в состояние; отправка в поток его не заменяет.

**`get_stream_writer` вне графа.** Вызванная в обычной функции, она не найдёт контекста прогона. Отправлять события можно только изнутри узла или инструмента.

**События с внутренностями.** Промпт, отправленный в модель, в потоке видит клиент. Один раз положив туда «на отладку» весь системный промпт, вы отдадите его наружу вместе с ответом.

**Ставка на экспериментальный API.** `v3` помечен как experimental и может измениться. Если вы его берёте, изолируйте разбор потока в одном месте — чтобы переписывать пришлось один файл, а не весь клиент.
