# Статические паузы и жизнь прерываний в проде

У `interrupt` есть более простой родственник — остановка перед узлом или после него, заданная при компиляции. Её задача другая: не спросить человека, а дать возможность вмешаться.

## `interrupt_before` и `interrupt_after`

```python
graph = builder.compile(
    checkpointer=saver,
    interrupt_before=["answer"],     # остановиться, не выполняя answer
)

result = graph.invoke(payload, config)   # дойдёт до answer и вернёт управление
```

Отличия от `interrupt` существенные, и их стоит держать в голове (проверено на langgraph 1.2.11):

| | `interrupt()` в узле | `interrupt_before` / `interrupt_after` |
|---|---|---|
| Где задаётся | в коде узла | при компиляции или на вызове |
| Передаёт человеку данные | да, любое значение | нет, просто останавливается |
| Виден в `__interrupt__` | да | **нет**: в результате обычное состояние |
| `snapshot.interrupts` | заполнен | пустой; остановка видна только по `next` |
| Продолжение | `Command(resume=...)` | `invoke(None, config)` |

Раз данных не передаётся, узнать о паузе можно только по снимку: `next` непустой, а запуск завершился. Именно поэтому статические паузы — инструмент отладки, а не общения с пользователем.

Зато они прекрасно сочетаются с правкой состояния:

```python
graph.invoke(payload, config)                       # остановились перед answer
graph.update_state(config, {"context": "..."})      # подменили контекст
graph.invoke(None, config)                          # доиграли
```

Проверено: состояние после такой правки — `['a', 'правка человека', 'b']`, то есть вмешательство встало между шагами.

Когда это нужно на практике: посмотреть, с каким промптом узел пойдёт в модель; подменить данные, чтобы воспроизвести жалобу; в Studio — пошагово прогнать граф. Задавать их можно и на конкретный вызов (`interrupt_before=[...]` прямо в `invoke`), не перекомпилируя граф.

## Что должно быть в приложении, чтобы паузы работали

Механизм сам по себе бесполезен, если вокруг него нет трёх вещей.

**Место, где видно ожидание.** Студент задал вопрос, получил встречный, закрыл вкладку. Завтра приложение должно показать тот же вопрос, а не начать заново. Источник истины — снимок: непустые `snapshot.interrupts` означают «ждём ответа», и показать надо значение прерывания.

**Права на ответ.** Отвечать на прерывание может только тот, чья это нить. Проверка простая, но её легко забыть, потому что в примерах из документации её нет: `thread_id` приходит от клиента, и никто не мешает подставить чужой. Сверяйте владельца нити с текущим пользователем **до** вызова графа.

**Проверка самого ответа.** То, что придёт в `Command(resume=...)`, — обычный внешний вход, такой же, как тело HTTP-запроса. Если узел ждёт `"решение"` или `"подсказка"`, а пришла строка на сто килобайт или словарь — узел должен это пережить. Валидируйте ответ там же, где принимаете, и не считайте, что клиент прислал одно из ваших значений.

```python
ALLOWED = {"решение", "подсказка"}


def offer_solution(state: TutorState) -> dict:
    choice = interrupt({"вопрос": "...", "варианты": sorted(ALLOWED)})
    if choice not in ALLOWED:
        choice = "подсказка"            # безопасное значение по умолчанию
    ...
```

## Сколько ждать

Граф ждёт вечно — это его свойство, а не проблема. Проблема появляется, когда таких нитей накапливаются тысячи: каждая держит снимок, и ни одна никогда не завершится.

Решения зависят от смысла паузы. Для наставника разумно: нить без ответа сутки — закрывается автоматически (отдельный процесс проходит по «висящим» нитям, отвечает безопасным значением и доигрывает граф). Для преподавательского разбора — напоминание, а не автозакрытие.

Найти такие нити можно перебором: у чекпойнтера есть метод перечисления, а признак ожидания — непустой `next` при отсутствии активности. Заведите этот процесс сразу: без него «висящие» нити обнаруживаются через полгода, когда кто-то заметит размер таблицы.

## Тестирование графов с паузами

Прерывания делают граф удобным для тестов: запуск детерминированно останавливается в известной точке.

```python
def test_спрашивает_перед_показом_решения():
    result = graph.invoke({"messages": [...], "mode": "homework"}, config)
    assert result["__interrupt__"][0].value["вопрос"].startswith("Показать готовое решение")

    final = graph.invoke(Command(resume="подсказка"), config)
    assert "решение" not in final["answer"].lower()
```

Отдельно проверьте то, что ломается чаще всего, — повторное выполнение узла: если в узле до `interrupt` есть запись, тест с подсчётом вызовов поймает удвоение. Подробно про тестирование — модуль 09.

## Типичные ошибки

**Статическая пауза вместо `interrupt`.** Пользователю нечего показать: значения нет, а сам факт остановки виден только в снимке.

**Ожидание `__interrupt__` от статической паузы.** Ключа в результате не будет, и код, который его ищет, решит, что граф завершился нормально.

**Ответ на прерывание без проверки прав.** Прямой путь к чужому разговору: `thread_id` — это то, что прислал клиент.

**Доверие к значению из `resume`.** Оно приходит снаружи и может быть любым.

**Нити, зависшие навсегда.** Заведите политику закрытия одновременно с первым прерыванием, а не когда их станет десять тысяч.
