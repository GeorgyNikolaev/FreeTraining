# Контекст запуска и внешние инструменты по MCP

Идентификатор студента, язык интерфейса, права доступа, имя курса — это данные, которые известны до запуска графа и не меняются в его ходе. Класть их в состояние можно, но неправильно: состояние предназначено для того, что узлы меняют, и каждое его поле уезжает в чекпойнт на каждом шаге.

Для неизменных данных есть отдельный механизм — контекст запуска.

## `context_schema` и `Runtime`

```python
from dataclasses import dataclass

from langgraph.graph import StateGraph
from langgraph.runtime import Runtime


@dataclass
class TutorContext:
    student_id: str
    locale: str = "ru"
    can_see_solutions: bool = False


def answer(state: TutorState, runtime: Runtime[TutorContext]) -> dict:
    if runtime.context.locale == "ru":
        prompt = "Отвечай по-русски."
    ...


builder = StateGraph(TutorState, context_schema=TutorContext)
```

Контекст передаётся при вызове отдельным аргументом — объектом или словарём:

```python
graph.invoke({"messages": [...]}, context=TutorContext(student_id="u-42"))
graph.invoke({"messages": [...]}, context={"student_id": "u-42", "locale": "en"})
```

Узел получает его, объявив параметр типа `Runtime[TutorContext]`; инструменты — через `runtime.context` у `ToolRuntime`. Кроме `context`, у `Runtime` есть `store`, `stream_writer` и служебные сведения о запуске.

| | Состояние | Контекст |
|---|---|---|
| Кто меняет | узлы по ходу работы | никто: задаётся на запуск |
| Попадает в чекпойнт | да | нет |
| Передаётся | первым аргументом `invoke` | параметром `context` |
| Что класть | сообщения, промежуточные результаты, флаги хода работы | идентификаторы, настройки, права, подключения |

Типичная ошибка новичка — забыть передать контекст. Узел тогда падает не на «контекста нет», а на обращении к полю: `AttributeError: 'NoneType' object has no attribute 'student_id'`. Увидев такое, проверяйте вызов, а не узел.

Контекст — хорошее место и для зависимостей: пула соединений к базе, клиента HTTP, настроек. Это избавляет узлы от глобальных переменных и делает граф тестируемым: в тесте вы передаёте поддельный клиент тем же параметром.

## Внешние инструменты по MCP

Инструменты не обязательно писать самому. Model Context Protocol (MCP) — открытый протокол, по которому внешние серверы отдают инструменты, и их можно подключить к агенту как обычные.

Пакет-адаптер ставится отдельно:

```bash
uv add langchain-mcp-adapters
```

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient(
    {
        "files": {
            "transport": "stdio",
            "command": "uvx",
            "args": ["mcp-server-filesystem", "/path/to/content"],
        },
        "internal": {
            "transport": "streamable_http",
            "url": "https://mcp.example.com/mcp",
        },
    }
)

tools = await client.get_tools()          # метод асинхронный
agent = create_agent(model=MODEL, tools=[*MY_TOOLS, *tools])
```

Поддерживаемые транспорты на версии адаптера 0.3.2 (сентябрь 2026): `stdio` — сервер запускается как подпроцесс, `streamable_http` и `sse` — по HTTP, `websocket`. Клиент умеет отдавать не только инструменты, но и промпты (`get_prompt`) и ресурсы (`get_resources`), а `tool_name_prefix` разводит одноимённые инструменты с разных серверов.

Когда MCP оправдан: инструмент уже существует как MCP-сервер (файловая система, база, трекер задач, поиск), его поддерживает кто-то другой, и писать свою обёртку смысла нет.

Когда не оправдан: инструменту нужен доступ к состоянию графа. Внешний сервер ничего не знает ни про `student_id`, ни про текущий урок — `ToolRuntime` ему недоступен. Всё, что связано с правами и данными конкретного студента, остаётся вашим кодом.

**Про доверие.** Инструменты с внешнего сервера приходят вместе со своими описаниями, а описание инструмента — это часть промпта. Сервер, которым вы не управляете, может влиять на поведение агента через тексты своих инструментов, а результат вызова — это тоже текст, который попадёт в модель. Подключайте только те серверы, которым доверяете так же, как своему коду; в модуле 10 разберём, что с этим делать, когда доверия нет.

## Что получает наставник

`TutorContext` со `student_id`, языком и признаком «можно ли показывать готовые решения» (пригодится в модуле 06), плюс пул соединений к Postgres. Внешние MCP-инструменты наставнику пока не нужны — все его данные лежат в этом же репозитории.

## Типичные ошибки

**Идентификатор студента в состоянии вместо контекста.** Работать будет, но поле уедет в каждый чекпойнт, и ничто не помешает узлу его переписать. Права доступа, которые может изменить узел, — плохая идея.

**Контекст как свалка.** В `context` кладут то, что нужно узлам, а не всё подряд. Он не сохраняется в чекпойнт, поэтому данные, нужные после перезапуска, там держать нельзя — их место в состоянии.

**Асинхронный `get_tools` в синхронном коде.** Метод асинхронный, и вызвать его при сборке графа «на месте» не получится. Инструменты MCP собирают при старте приложения, до компиляции графа.

**MCP-сервер как источник правды о пользователе.** Ещё раз: внешний инструмент не знает, кто спрашивает. Если он что-то возвращает про «текущего пользователя», это данные его сервера, а не вашего студента.
