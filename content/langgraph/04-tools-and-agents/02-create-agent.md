# Готовый агент: `create_agent` и когда его достаточно

Цикл из прошлого урока собран настолько типовым образом, что в LangChain есть фабрика, которая делает то же самое одной строкой. Понимать её стоит по двум причинам: половину задач она закрывает целиком, а вторую половину — закрывает частично, и надо уметь увидеть границу.

```python
from langchain.agents import create_agent

agent = create_agent(
    model=os.environ["TUTOR_MODEL"],
    tools=[search_lessons, get_progress],
    system_prompt="Ты наставник на учебной платформе. Отвечай со ссылками на уроки.",
)

result = agent.invoke({"messages": [{"role": "user", "content": "что такое редьюсер?"}]})
print(result["messages"][-1].text)
```

Возвращается обычный скомпилированный граф LangGraph — тот же объект, что получается из `builder.compile()`. Значит, ему доступно всё, что мы разберём дальше: чекпойнты, прерывания, стриминг, подграфы.

## Что он принимает

На сентябрь 2026 (`langchain` 1.4) у `create_agent` такие параметры: `model`, `tools`, `system_prompt`, `middleware`, `response_format`, `state_schema`, `context_schema`, `checkpointer`, `store`, `interrupt_before`, `interrupt_after`, `cache`, `name`, `debug`.

Два из них стоит отметить сразу. `response_format` заставляет агента вернуть структурированный ответ (например, объект с полями «ответ» и «использованные уроки»), а `state_schema` позволяет расширить состояние своими полями — но только на `TypedDict`: Pydantic-схемы состояния `create_agent` не поддерживает.

## Middleware: куда вклиниться, не разбирая граф

Между «одна строка» и «свой граф» есть промежуточная ступень — middleware, перехватчики вокруг вызова модели и инструментов. Их в `langchain.agents.middleware` несколько десятков; вот те, что чаще всего нужны наставнику:

| Middleware | Что делает |
|---|---|
| `SummarizationMiddleware` | сжимает разросшуюся историю диалога |
| `ModelCallLimitMiddleware` | ограничивает число вызовов модели за запуск |
| `ToolCallLimitMiddleware` | то же для инструментов — страховка от зацикливания |
| `HumanInTheLoopMiddleware` | требует подтверждения человека перед указанными инструментами |
| `ToolRetryMiddleware`, `ToolErrorMiddleware` | повторы и обработка ошибок инструментов |
| `ModelFallbackMiddleware` | переключение на запасную модель |
| `PIIMiddleware` | вырезает персональные данные |
| `ContextEditingMiddleware` | чистит контекст от устаревших результатов инструментов |

```python
from langchain.agents.middleware import ModelCallLimitMiddleware, SummarizationMiddleware

agent = create_agent(
    model=os.environ["TUTOR_MODEL"],
    tools=TOOLS,
    system_prompt=PROMPT,
    middleware=[
        ModelCallLimitMiddleware(thread_limit=10),
        SummarizationMiddleware(model=os.environ["TUTOR_MODEL"], max_tokens_before_summary=4000),
    ],
)
```

Подробно middleware — тема курса по LangChain. Здесь важно правило выбора: middleware настраивает поведение стандартного цикла, а граф нужен тогда, когда меняется сама форма процесса.

## Когда хватает фабрики, а когда нужен свой граф

| Задача | Чем делать |
|---|---|
| Диалог «модель ↔ инструменты», возможно с памятью и подтверждениями | `create_agent` |
| То же плюс ограничения, сжатие истории, запасная модель | `create_agent` + middleware |
| До вызова модели нужен свой шаг: классификация, загрузка контекста, проверка прав | свой граф |
| После инструментов — своя маршрутизация, а не всегда обратно в модель | свой граф |
| Процесс не сводится к одному циклу: проверка ДЗ веером, отчёт из нескольких стадий | свой граф |
| Несколько агентов с передачей управления | свой граф (модуль 08) |

Наставник в итоге окажется во второй половине таблицы: у него есть и классификация до модели, и проверка ДЗ веером, и подтверждение перед выдачей решения. Но это не значит, что `create_agent` ему не нужен.

## Готовый агент как узел своего графа

Самый практичный приём этого урока: не выбирать между фабрикой и графом, а вложить одно в другое.

```python
research = create_agent(model=MODEL, tools=[search_lessons], system_prompt="Найди, где в курсе об этом говорилось.")


def research_node(state: TutorState) -> dict:
    result = research.invoke({"messages": state["messages"]})
    return {"messages": [result["messages"][-1]]}


builder.add_node("research", research_node)
```

Внешний граф отвечает за форму процесса (классификация → поиск → ответ → проверка), а внутри одного шага крутится готовый ReAct-цикл, который не надо описывать руками. В модуле 08 мы сделаем то же самое аккуратнее — вложенным подграфом, без ручной перекладки сообщений.

## Типичные ошибки

**Фабрика вместо понимания.** `create_agent` не делает агента умнее: это тот же цикл, который мы собрали руками. Если агент выбирает не те инструменты, фабрика не поможет — чинить надо докстринги и промпт.

**Свой граф вместо настройки.** Обратная ошибка: переписывать цикл руками, потому что нужно ограничить число вызовов модели. Для этого есть middleware, и он не требует своего графа.

**Ожидание, что `state_schema` примет Pydantic-модель.** На сентябрь 2026 не примет. Если состояние агента должно валидироваться — это аргумент в пользу своего графа.

**Смешение уровней в одном месте.** Если вы уже обложили `create_agent` пятью middleware и всё равно дописываете логику снаружи, скорее всего, процесс перерос фабрику. Перенос в явный граф в этот момент обойдётся дешевле, чем через три месяца.
