# Инструменты, которые знают, кто спрашивает

Инструмент `search_lessons` из первого урока модуля — чистая функция: что передали, то и обработала. Но наставнику нужны и другие: «какие темы студент завалил», «на каком он уроке», «открой урок и запомни, что мы им пользовались». Таким инструментам нужен доступ к состоянию графа и к сведениям о запуске.

## `ToolRuntime`: состояние, идентификатор вызова, хранилище

Чтобы инструмент получил контекст исполнения, ему добавляют параметр с типом `ToolRuntime`. Модель этого параметра **не видит** — он не попадает в схему аргументов и заполняется движком.

```python
from langchain.tools import tool
from langgraph.prebuilt import ToolRuntime


@tool
def get_progress(runtime: ToolRuntime) -> str:
    """Показать прогресс студента: пройденные уроки и результаты тестов.

    Используй, когда студент спрашивает про свои результаты или просит
    подсказать, что повторить.
    """
    student_id = runtime.state["student_id"]
    rows = fetch_progress(student_id)          # обычный запрос в Postgres
    return format_progress(rows)
```

Что доступно через `runtime` (langgraph 1.2.11): `state` — текущее состояние графа, `context` — неизменяемый контекст запуска (следующий урок), `config` — конфигурация вызова, `store` — долговременная память (модуль 05), `tool_call_id` — идентификатор этого вызова, `stream_writer` — канал для своих событий в поток (модуль 07), плюс сведения об исполнении и сервере.

Практический смысл: идентификатор студента **не должен быть аргументом инструмента**. Аргументы заполняет модель, а значит, их можно подсказать ей в тексте вопроса: «покажи прогресс студента u-1». Через `runtime.state` такой подмены не происходит — значение приходит из состояния, которое заполнил ваш код.

## Инструмент, меняющий состояние

Обычный инструмент возвращает строку, и `ToolNode` сам заворачивает её в `ToolMessage`. Но инструмент может вернуть `Command` — тогда он обновит состояние графа:

```python
from langchain.messages import ToolMessage
from langgraph.types import Command


@tool
def open_lesson(lesson_id: str, runtime: ToolRuntime) -> Command:
    """Открыть текст урока и запомнить его как использованный источник."""
    text = read_lesson(lesson_id)
    return Command(
        update={
            "sources": [lesson_id],
            "messages": [
                ToolMessage(content=text[:2000], tool_call_id=runtime.tool_call_id)
            ],
        }
    )
```

Здесь важна деталь, на которой спотыкаются все: **`ToolMessage` придётся создать самому, и в нём обязателен `tool_call_id`**. Когда инструмент возвращает `Command`, автоматической упаковки результата не происходит. Если сообщение не добавить, в истории останется вызов инструмента без ответа — а большинство провайдеров на такую историю отвечают ошибкой, потому что протокол требует ответа на каждый `tool_call`.

Проверено на langgraph 1.2.11: три вызова в одном сообщении — обычный инструмент, инструмент с `Command` и падающий инструмент — дают три `ToolMessage` и обновлённое поле `sources`.

## Ошибки внутри инструмента

По умолчанию исключение внутри инструмента **роняет весь запуск**: `ToolNode` его перебрасывает наружу. Это разумное значение по умолчанию (ошибка не проходит незамеченной), но для агента обычно нужно другое поведение — сообщить модели о неудаче и дать ей выбрать другой путь.

```python
tool_node = ToolNode(
    TOOLS,
    handle_tool_errors="Инструмент недоступен. Попробуй ответить без него или уточни вопрос.",
)
```

| Значение `handle_tool_errors` | Поведение |
|---|---|
| не задано | исключение пробрасывается, запуск падает |
| строка | модель получает `ToolMessage` с этим текстом |
| `True` | модель получает сообщение с текстом исключения |
| функция | текст сообщения формируете вы, по типу исключения |

Функция удобна, когда сбои надо различать: «урок не найден» стоит показать модели дословно (она подскажет правильный идентификатор), а «база недоступна» — заменить нейтральной фразой, чтобы не выкладывать в диалог внутренности.

Не забывайте: текст ошибки уходит в модель, а оттуда — в ответ студенту. Строка подключения к базе в тексте исключения окажется на экране.

## Что получает наставник

| Инструмент | Что берёт из `runtime` | Зачем |
|---|---|---|
| `search_lessons` | ничего | чистый поиск по файлам курса |
| `get_progress` | `state["student_id"]` | нельзя позволить модели подставить чужой идентификатор |
| `open_lesson` | `tool_call_id` | возвращает `Command` и сам собирает `ToolMessage` |
| `remember_fact` | `store` | пишет в долговременную память (модуль 05) |

## Типичные ошибки

**Идентификатор пользователя как аргумент инструмента.** Самая опасная ошибка урока: она превращает безобидный вопрос в способ прочитать чужие данные. Всё, что определяет права доступа, берётся из состояния или контекста, а не из аргументов, которые заполняет модель.

**`Command` без `ToolMessage`.** Граф отработает, а следующий вызов модели упадёт с ошибкой протокола — и выглядеть это будет как проблема провайдера.

**`handle_tool_errors=True` в проде.** Текст исключения уходит модели целиком. Для разработки удобно, для прода — способ показать студенту трассировку.

**Инструмент, который делает необратимое, без подтверждения.** Пока инструменты только читают, это неважно. Как только появится «отметить урок пройденным» или «сбросить прогресс», понадобится пауза для человека — модуль 06.
