# Functional API: те же гарантии без графа

Весь курс мы описывали процесс как граф: узлы, рёбра, состояние. Есть и второй способ — написать обычную функцию с обычным потоком управления и получить те же чекпойнты, прерывания и стриминг. Называется он Functional API.

## `entrypoint` и `task`

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task


@task
def find_lesson(query: str) -> str:
    return search(query)


@task
def write_answer(lesson: str, question: str) -> str:
    return model.invoke(...).text


@entrypoint(checkpointer=InMemorySaver())
def tutor(question: str) -> str:
    lesson = find_lesson(question).result()
    return write_answer(lesson, question).result()


tutor.invoke("что такое редьюсер?", {"configurable": {"thread_id": "t-1"}})
```

Два декоратора и обычный Python между ними: `if`, циклы, ранние возвраты — всё как в любой функции.

- `@task` помечает шаг, результат которого сохраняется. Вызов возвращает будущее, `.result()` дожидается значения. Несколько задач, запущенных до первого `.result()`, выполняются параллельно.
- `@entrypoint` делает из функции точку входа с чекпойнтером, хранилищем, контекстом и политиками — параметры те же, что у графа: `checkpointer`, `store`, `context_schema`, `retry_policy`, `cache_policy`, `timeout`.

Возвращается при этом объект того же типа, что и скомпилированный граф: у него есть `invoke`, `stream`, `get_state`. Проверено на langgraph 1.2.11: `tutor.get_state(config).values` отдаёт сохранённый результат, как у обычного графа.

Прерывания работают так же: `interrupt` внутри задачи останавливает выполнение, `Command(resume=...)` продолжает.

## Чем это отличается от графа

Разница не в возможностях, а в том, что видно и что сохраняется.

| | Граф (`StateGraph`) | Functional API |
|---|---|---|
| Поток управления | рёбрами, явно | обычным Python |
| Схема | рисуется, видна в Studio | нет: это просто функция |
| Состояние | объявленная схема с редьюсерами | локальные переменные функции |
| Что сохраняется | состояние после каждого шага | результаты задач и итог |
| Возобновление после сбоя | с прерванного узла | функция запускается заново, выполненные задачи берутся из сохранённого |
| Редактирование состояния снаружи | `update_state` | нет прямого аналога |
| Человек в цикле, стриминг, Store | да | да |

Ключевое здесь — предпоследняя строка. При возобновлении **тело функции выполняется с начала**, а задачи, которые уже отработали, не пересчитываются: их результаты подставляются из сохранённого. Логика та же, что у повторного выполнения узла с `interrupt` в модуле 06, и требование то же: всё, что меняет мир, должно быть внутри `@task`, а не в теле функции.

## Что выбрать

| Ситуация | Выбор |
|---|---|
| Процесс ветвится, и структуру хочется видеть | граф |
| Нужно вмешиваться в состояние снаружи, ходить по истории, откатываться | граф |
| Процесс линейный или ветвится обычными `if`, но нужны чекпойнты и паузы | Functional API |
| Есть готовая функция на сто строк, которой не хватает надёжности | Functional API: разметить задачами быстрее, чем переписывать в граф |
| Несколько агентов, подграфы, супервизор | граф |

Для наставника выбор — граф: у него ветвление, прерывания в разных местах, отладка по схеме и правка состояния. Но одно место в проекте идеально ложится на Functional API — ночной обход курса из модуля 10: «для каждого урока проверить противоречия и собрать отчёт». Это линейный процесс с параллельными задачами, которому нужны только надёжность и возобновление после сбоя.

```python
@entrypoint(checkpointer=saver)
def audit_course(course_id: str) -> dict:
    lessons = list_lessons(course_id)
    futures = [check_lesson(lesson) for lesson in lessons]   # параллельно
    return summarize([f.result() for f in futures])
```

Писать то же самое графом пришлось бы через `Send`, схему состояния и узел-сборщик с `defer=True` — ради процесса, у которого нет ни одного ветвления.

## Типичные ошибки

**Побочные эффекты в теле `entrypoint`.** При возобновлении тело выполняется заново: запись в базу, стоящая между задачами, повторится. Всё необратимое — внутри `@task`.

**Недетерминированность в теле.** `random`, текущее время, обход словаря в произвольном порядке — при повторном проходе дадут другой результат, и подстановка сохранённых результатов задач перестанет соответствовать логике. Недетерминированное тоже заворачивают в задачу.

**Вызов `.result()` сразу после каждой задачи.** Параллельность теряется: запускайте все задачи, потом собирайте результаты.

**Выбор Functional API ради краткости.** Если процесс ветвистый, отсутствие схемы будет стоить дороже сэкономленных строк — особенно при отладке через полгода.
