# Долговременная память и подрезка истории

Нить помнит разговор. Но «этот студент раз за разом путает редьюсер с маршрутизатором» — знание не про разговор, а про человека: оно должно пережить и конец диалога, и переход к другому курсу. Для такого в LangGraph есть отдельное хранилище — Store.

## Store: пространства имён, ключи, значения

```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
ns = ("students", "u-42", "facts")

store.put(ns, "fact-1", {"text": "путает редьюсер и маршрутизатор",
                         "lesson": "langgraph/02-graph-and-state/02-reducers"})
store.put(ns, "fact-2", {"text": "просит примеры на async"})

store.get(ns, "fact-1").value            # {'text': ..., 'lesson': ...}
store.search(ns)                         # оба факта
store.search(ns, filter={"lesson": "langgraph/02-graph-and-state/02-reducers"})
```

Пространство имён — кортеж строк, и это не просто ключ, а иерархия: поиск идёт по префиксу. `("students", "u-42")` найдёт и факты, и предпочтения, и что угодно ещё, что вы положили в подпространства этого студента.

У `put` есть параметр `ttl` — срок жизни записи. Для фактов вроде «сейчас проходит модуль 5» это разумнее, чем помнить вечно.

Store подключается при компиляции, а узлы и инструменты берут его из `Runtime`:

```python
graph = builder.compile(checkpointer=saver, store=store)


def recall(state: TutorState, runtime: Runtime[TutorContext]) -> dict:
    facts = runtime.store.search(("students", runtime.context.student_id, "facts"), limit=5)
    hints = "\n".join(f"- {item.value['text']}" for item in facts)
    return {"memory_hint": hints}
```

В проде вместо `InMemoryStore` берут `PostgresStore` из пакета `langgraph-checkpoint-postgres`; ему, как и чекпойнтеру, нужен разовый `setup()`.

## Семантический поиск

Точное совпадение по ключам работает, пока фактов мало. Когда их сотни, нужен поиск по смыслу — Store умеет и это, если задать при создании конфигурацию индекса:

```python
from langchain_openai import OpenAIEmbeddings

store = InMemoryStore(index={"embed": OpenAIEmbeddings(model="text-embedding-3-small"),
                             "dims": 1536,
                             "fields": ["text"]})

store.search(("students", "u-42", "facts"), query="что у него не получается с состоянием")
```

`fields` задаёт, какие поля значения векторизуются. `PostgresStore` делает то же самое на pgvector — расширение придётся включить в базе.

Это единственное место в курсе, где появляется векторный поиск, и намеренно: инфраструктура RAG — тема отдельная, а здесь нам нужно ровно «найти похожие факты о студенте».

## Что наставнику стоит помнить о студенте

Соблазн — писать в память всё подряд. Полезнее договориться о составе заранее:

| Пространство | Что храним | Кто пишет |
|---|---|---|
| `("students", id, "facts")` | устойчивые наблюдения: где путается, что уже понял | узел после проверки ДЗ или разбора теста |
| `("students", id, "prefs")` | предпочтения: язык примеров, длина ответов, «не показывай решения сразу» | инструмент, когда студент попросил явно |
| `("students", id, "progress_notes")` | заметки о пройденном, которых нет в базе прогресса | узел в конце разговора |

И правило, которое экономит много неловкости: память пишется **осознанно**, отдельным шагом или инструментом, а не автоматически из каждой реплики. Агент, запоминающий всё, быстро набирает мусор («студент поздоровался») и случайные выводы, которые потом влияют на ответы.

## Подрезка истории

Вторая половина урока — про обратное: что забывать. История в `messages` растёт, уходит в модель целиком на каждом шаге и целиком же пишется в каждый чекпойнт.

Простой и предсказуемый способ — оставлять хвост:

```python
from langchain.messages import RemoveMessage


def trim_history(state: TutorState) -> dict:
    keep = 20
    extra = state["messages"][:-keep]
    return {"messages": [RemoveMessage(id=m.id) for m in extra]}
```

Помните из модуля 02: `add_messages` понимает `RemoveMessage` как удаление по идентификатору, а `RemoveMessage(id=REMOVE_ALL_MESSAGES)` очищает историю целиком.

Способ по токенам, а не по числу сообщений, — `trim_messages` из LangChain: у него есть `max_tokens`, `token_counter` и стратегия (`"last"` — оставить конец, `"first"` — начало).

Есть и третий путь — сжимать вытесняемое в краткое резюме, которое остаётся в состоянии отдельным полем; в готовом агенте за это отвечает `SummarizationMiddleware` (модуль 04).

Что выбрать наставнику: хвост из 20 сообщений плюс резюме предыдущего разговора в долговременной памяти. Резюме — это как раз тот случай, когда запись в Store делается осознанно: в конце разговора, одним шагом.

**Осторожно с обрезкой в середине цепочки инструментов.** Удаление сообщений — операция над протоколом: если вырезать `AIMessage` с вызовом инструмента, а его `ToolMessage` оставить, история станет невалидной и провайдер ответит ошибкой. Обрезайте по границам законченных ходов.

## Типичные ошибки

**Store вместо базы приложения.** Прогресс, результаты тестов, профиль — это данные платформы, им место в её таблицах, откуда их берёт инструмент. В Store — только то, что вывел сам агент.

**Память без пространства имён пользователя.** Ключ вида `("facts", "fact-1")` перемешает студентов. Идентификатор пользователя — обязательная часть пространства имён, и брать его надо из контекста запуска, а не из аргументов модели.

**Запись фактов моделью без разбора.** «Запомни, что я всё понял» — и агент начинает считать, что студент разобрался в редьюсерах. Факты в памяти должны иметь источник: не «модель так решила», а «проверка ДЗ показала».

**Подрезка, ломающая пары вызов–ответ.** Самая частая поломка обрезки: ошибка приходит от провайдера и выглядит как проблема модели, а причина — в осиротевшем `tool_call`.

**Память, которую нельзя забыть.** Если агент помнит о студенте, должен быть способ это стереть: и по-человечески, и по требованиям к персональным данным. Сделайте инструмент «забудь про меня» сразу, а не когда попросят.
