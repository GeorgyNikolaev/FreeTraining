# Postgres под нитями и цена записи

`InMemorySaver` живёт в процессе: перезапуск — и разговоров нет. Для платформы это не годится, тем более что Postgres в `docker-compose.yml` уже поднят и держит прогресс студентов.

## Подключение

```bash
uv add langgraph-checkpoint-postgres
```

```python
# agent/tutor/checkpointer.py
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

DSN = "postgresql://freetraining:freetraining@localhost:5433/freetraining"


async def build_graph():
    async with AsyncPostgresSaver.from_conn_string(DSN) as saver:
        await saver.setup()               # один раз: создаёт таблицы и накатывает миграции
        yield builder.compile(checkpointer=saver)
```

`setup()` обязателен при первом использовании — сам чекпойнтер таблицы не создаёт. Вызывать его при каждом старте безопасно (повторный вызов ничего не ломает), но правильнее — на деплое, вместе с остальными миграциями.

Асинхронная версия (`AsyncPostgresSaver` из `langgraph.checkpoint.postgres.aio`) нужна, если граф вызывается из асинхронного кода — а в FastAPI это так. Синхронный `PostgresSaver` лежит в `langgraph.checkpoint.postgres`. Мешать их нельзя: синхронный чекпойнтер в асинхронном графе заблокирует цикл событий.

В веб-приложении соединение берут не строкой, а пулом, который живёт всё время работы приложения. Версия пакета на сентябрь 2026 — 3.1.x, под капотом `psycopg` 3.

## Что появляется в базе

`setup()` создаёт несколько таблиц: сами чекпойнты, значения каналов и «записи» — обновления, ещё не вошедшие в снимок. Это отдельная от вашей предметной схемы область: таблицы прогресса и таблицы чекпойнтов не пересекаются, и лезть в чекпойнты запросами не нужно — всё, что оттуда требуется, отдаёт API графа.

Удаление тоже через API: у чекпойнтера есть методы удаления нити и очистки старых снимков. Это важнее, чем кажется: нити копятся, и без политики удаления таблица чекпойнтов однажды станет самой большой в базе.

## `durability`: чем платим за надёжность

Запись снимка — это запрос в базу на каждом шаге графа. Режим записи задаётся параметром `durability` при вызове:

```python
await graph.ainvoke(payload, config, durability="sync")
```

| Режим | Когда пишется снимок | Чем платим | Когда выбирать |
|---|---|---|---|
| `"sync"` | синхронно, до начала следующего шага | задержка каждого шага | деньги/необратимые действия: потерять шаг нельзя |
| `"async"` | асинхронно, параллельно следующему шагу | при падении может потеряться последний снимок | **по умолчанию**; подходит почти всем |
| `"exit"` | только при завершении графа | при падении теряется весь прогресс запуска | короткие запуски, где важнее скорость |

По умолчанию — `"async"` (проверено на langgraph 1.2.11).

Как выбирать. Наставник в режиме вопросов и ответов прекрасно живёт на `"async"`: потеря последнего шага в худшем случае означает повтор вопроса. А вот граф, который отмечает урок пройденным и начисляет баллы, должен идти на `"sync"` — иначе после сбоя непонятно, записалось начисление или нет.

Режим `"exit"` выглядит соблазнительно быстрым, но у него есть скрытая цена: пока граф не завершился, снаружи не видно ни промежуточного состояния, ни возможности продолжить с середины. Прерывания для человека в цикле с ним, по сути, бессмысленны.

## Асинхронность узлов

Раз чекпойнтер асинхронный, узлы тоже стоит писать асинхронными:

```python
async def answer(state: TutorState) -> dict:
    reply = await model.ainvoke(...)
    return {"answer": reply.text}
```

Это даёт три вещи разом: неблокирующую работу в FastAPI, возможность ставить таймауты узлам (модуль 03 — они только для асинхронных) и честную параллельность веера `Send`, когда узлы ждут сеть.

Смешивать можно: синхронные узлы в асинхронном графе работают, движок выполнит их в отдельном потоке. Но узел, который ходит в сеть синхронно, съедает поток на всё время ожидания — на нагрузке это первое, что упрётся.

## Сколько это стоит

Прикиньте на своём случае: снимок — это состояние целиком, а не разница. Диалог из 40 сообщений по 500 токенов — примерно 80 КБ состояния; при `durability="async"` это 80 КБ записи на каждом шаге графа, а шагов в одном ответе наставника — от трёх до десяти.

Отсюда практические выводы: не держите в состоянии то, что можно перечитать (тексты уроков — по идентификаторам, а не целиком), подрезайте историю сообщений, а для долгих нитей смотрите в сторону `ShallowPostgresSaver`, который хранит только последний снимок — ценой отказа от истории и путешествия во времени.

В langgraph 1.2 появился ещё один инструмент для длинных нитей — канал, хранящий только приращения вместо полного значения (`DeltaChannel`). На сентябрь 2026 он в статусе беты; если нить растёт бесконтрольно, это первое, куда стоит заглянуть.

## Типичные ошибки

**Забытый `setup()`.** Граф падает на первом же обращении к базе с ошибкой об отсутствующей таблице. Лечится одной строкой, но ищут её долго, потому что ошибка выглядит как проблема подключения.

**Синхронный чекпойнтер в асинхронном приложении.** Работает — и блокирует цикл событий на каждом шаге. Под нагрузкой это выглядит как «FastAPI почему-то тормозит на всех запросах».

**Соединение на каждый вызов.** `from_conn_string` в обработчике запроса открывает соединение на каждый вопрос студента. Пул создаётся один раз при старте приложения.

**`durability="exit"` ради скорости.** Экономия реальна, но вместе с ней исчезает всё, ради чего чекпойнтер ставили: продолжение после сбоя и паузы для человека.

**Нити, которые никто не удаляет.** Заведите правило: нити без активности старше N месяцев удаляются. Иначе про эту таблицу вы вспомните, когда кончится место.
