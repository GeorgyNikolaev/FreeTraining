# Несколько схем: вход, выход и приватные поля

К концу прошлого урока в состоянии наставника завелись поля, которых там быть не должно: снаружи в граф передают вопрос и урок, а `context`, `is_on_topic` и `reason` — внутренняя кухня. Если оставить одну схему на всё, вызывающий код увидит эту кухню, а с ней и соблазн в неё лезть.

## Три схемы вместо одной

`StateGraph` принимает схему состояния и, дополнительно, схемы входа и выхода.

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph


class TutorInput(TypedDict):
    question: str
    lesson_id: str


class TutorOutput(TypedDict):
    answer: str
    sources: list[str]


class TutorState(TypedDict):
    question: str
    lesson_id: str
    is_on_topic: bool
    reason: str
    context: str
    answer: str
    sources: list[str]


builder = StateGraph(
    TutorState,
    input_schema=TutorInput,
    output_schema=TutorOutput,
)
```

Теперь `graph.invoke({"question": ..., "lesson_id": ...})` возвращает только `{"answer": ..., "sources": [...]}` — ни `context`, ни `reason` в ответе не будет. Внутри графа узлы по-прежнему работают с полной `TutorState`.

Зачем это нужно:

- **Контракт наружу.** Веб-обработчик, который в модуле 07 будет звать граф, зависит от двух полей, а не от семи. Внутренности можно переименовать, не трогая вызывающий код.
- **Меньше мусора в ответе.** Текст урока в `context` — это десятки килобайт, которые незачем гонять в HTTP-ответе.

Чего это **не** делает: схема выхода фильтрует только то, что возвращает `invoke`. В сохранённом состоянии остаются все поля — в модуле 05 мы увидим их целиком в снимке.

## Приватное поле между двумя узлами

Бывает, что значение нужно передать из одного узла ровно в соседний: черновик, промежуточная оценка, разметка. Класть его в общую схему — значит навсегда поселить в состоянии поле, которое интересно двум узлам из восьми.

Для этого у узла может быть своя схема входа:

```python
class Draft(TypedDict):
    draft_answer: str


def write_draft(state: TutorState) -> Draft:
    return {"draft_answer": "..."}


def polish(state: Draft) -> dict:
    return {"answer": state["draft_answer"].strip()}


builder.add_node("write_draft", write_draft)
builder.add_node("polish", polish, input_schema=Draft)
```

Узел `polish` объявлен с `input_schema=Draft`, поэтому получает не всё состояние, а только объявленные им поля. Остальные узлы `draft_answer` не видят и не могут случайно на него опереться.

Приём полезный, но злоупотреблять им не стоит: каждая дополнительная схема — ещё одно место, которое надо держать в голове при чтении графа. Приватный канал оправдан там, где промежуточное значение большое или неинтересно никому, кроме пары узлов.

## Чем описывать состояние: `TypedDict`, `dataclass` или Pydantic

| Способ | Значения по умолчанию | Валидация | Цена | Когда брать |
|---|---|---|---|---|
| `TypedDict` | нет | нет | минимальная | по умолчанию; так написано большинство примеров в документации |
| `dataclass` | есть (`field(default_factory=...)`) | нет | минимальная | когда надоело передавать пустые списки во входном словаре |
| Pydantic `BaseModel` | есть | есть | заметная | когда в состояние попадают данные извне и им нельзя верить |

С `dataclass` узел получает объект, и поля читаются через точку — `state.question` вместо `state["question"]`. Возвращает узел по-прежнему словарь с обновлениями.

```python
from dataclasses import dataclass, field


@dataclass
class TutorState:
    question: str
    lesson_id: str
    sources: list[str] = field(default_factory=list)
    answer: str = ""
```

Вызывать такой граф можно и объектом (`graph.invoke(TutorState(question="...", lesson_id="..."))`), и обычным словарём — движок сам соберёт объект.

У Pydantic-схемы есть особенность, про которую стоит знать заранее. Валидация срабатывает **не в момент, когда узел вернул обновление, а когда состояние передаётся в следующий узел**. Проверено на langgraph 1.2.11: узел, записавший в поле `score: int` строку, отрабатывает спокойно, а падает соседний:

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for PState
score
  Input should be a valid integer, unable to parse string as an integer
Before task with name 'probe' and path '('__pregel_pull', 'probe')'
```

Отсюда два следствия. Первое: ищите виновника не там, где упало, — писал плохое значение предыдущий узел. Второе: если узел с плохой записью оказался последним, валидация не сработает вовсе и невалидное значение уедет наружу.

Ещё одно ограничение на сентябрь 2026: фабрика `create_agent` из LangChain (её мы разберём в модуле 04) Pydantic-схемы состояния не поддерживает. Если планируете строить агента на ней, берите `TypedDict`.

## Типичные ошибки

**Схема выхода как средство спрятать данные.** Поле, исключённое из `output_schema`, никуда не исчезает: оно в состоянии, в снимках, в трейсе LangSmith. Секретам в состоянии не место независимо от схем.

**Раздутая общая схема.** Когда каждое промежуточное значение получает своё поле, состояние превращается в глобальные переменные: любой узел читает и пишет что угодно, и через месяц никто не знает, кто заполняет `flag2`. Приватные схемы узлов и есть лекарство.

**Вход, который нельзя вызвать.** Если в `input_schema` попало поле, которое на самом деле заполняет первый узел, вызывающему коду придётся передавать пустышку. Во входной схеме должно быть ровно то, что известно до запуска графа.
