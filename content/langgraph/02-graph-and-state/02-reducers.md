# Редьюсеры: как обновления складываются с состоянием

По умолчанию обновление поля заменяет его значение. Для `answer` это правильно, для истории сообщений — катастрофа: каждый новый ход стирал бы предыдущий. Редьюсер (reducer) — функция, которая решает, как объединить текущее значение поля с тем, что вернул узел.

## Замена по умолчанию и её граница

Возьмём состояние из прошлого урока и добавим накопление ссылок на уроки, которыми наставник подкрепляет ответ.

```python
class TutorState(TypedDict):
    question: str
    sources: list[str]
```

Если узел вернёт `{"sources": ["01-what-is-langgraph.md"]}`, а следующий — `{"sources": ["02-reducers.md"]}`, в состоянии останется только второй список. Первый исчезнет: по умолчанию новое значение просто вытесняет старое.

У замены есть и жёсткая граница. Два узла, работающие параллельно, не могут записать в одно и то же поле — движок не знает, чьё значение оставить, и падает:

```
langgraph.errors.InvalidUpdateError: At key 'sources': Can receive only one value per step.
Use an Annotated key to handle multiple values.
```

Текст ошибки и есть инструкция: пометьте поле редьюсером.

## Как объявляется редьюсер

Редьюсер прикрепляется к полю через `Annotated`: первый аргумент — тип значения, второй — функция объединения.

```python
from operator import add
from typing import Annotated
from typing_extensions import TypedDict


class TutorState(TypedDict):
    question: str
    answer: str                            # замена: нужен только последний ответ
    sources: Annotated[list[str], add]     # накопление: списки складываются
```

`add` здесь — обычный `operator.add`, для списков это конкатенация. Теперь два узла могут писать в `sources` параллельно, и оба списка окажутся в состоянии.

Редьюсер вызывается **при каждом** обновлении поля, не только при параллельном. Сигнатура — два аргумента: текущее значение (в документации `left`) и обновление от узла (`right`); возвращается новое значение поля.

## Свой редьюсер

`add` копит всё подряд, включая повторы. Наставнику это не подходит: если три узла сослались на один и тот же урок, студент не должен увидеть его трижды.

```python
def merge_sources(left: list[str] | None, right: list[str] | None) -> list[str]:
    """Копит ссылки без повторов. Пустой список справа означает сброс."""
    if right == []:
        return []
    merged = list(left or [])
    for item in right or []:
        if item not in merged:
            merged.append(item)
    return merged


class TutorState(TypedDict):
    sources: Annotated[list[str], merge_sources]
```

Два приёма в этих шести строках стоят того, чтобы их запомнить.

Первый: `left` может прийти пустым или `None` — при первом обновлении поля складывать не с чем. Редьюсер, начинающийся с `left.append(...)`, упадёт на первом же запуске.

Второй: поле с накопительным редьюсером **нельзя сбросить обычным присваиванием**. Узел, вернувший `{"sources": []}`, по логике `add` просто добавит пустой список — значение останется прежним. Если сброс нужен (например, начался новый вопрос и старые ссылки неактуальны), его придётся предусмотреть в самом редьюсере — как сделано выше через `right == []`.

Требования к редьюсеру: он должен быть чистым (никаких запросов в базу и записи в файлы) и быстрым — движок зовёт его на каждом обновлении. И не полагайтесь на порядок, в котором приходят обновления от параллельных веток: если результат зависит от порядка, вы получите плавающее поведение.

## `add_messages` — редьюсер для истории диалога

История сообщений — самое частое поле состояния, и у неё свой редьюсер `add_messages`, который умеет больше, чем конкатенация.

```python
from typing import Annotated

from langchain.messages import AnyMessage
from langgraph.graph.message import add_messages
from typing_extensions import TypedDict


class TutorState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```

Что он делает (поведение проверено на langgraph 1.2.11):

| Что вернул узел | Что произойдёт |
|---|---|
| Сообщение с новым `id` или без `id` | добавится в конец; отсутствующий `id` будет сгенерирован |
| Сообщение с `id`, который уже есть в списке | **заменит** это сообщение, а не добавится |
| `RemoveMessage(id="2")` | удалит сообщение с этим `id` |
| `RemoveMessage(id=REMOVE_ALL_MESSAGES)` | очистит историю целиком |
| Словарь `{"role": "user", "content": "..."}` | превратится в `HumanMessage` |

Замена по `id` — то, ради чего стоит держать `add_messages` вместо `add`. Она позволяет исправить уже записанное сообщение: например, вырезать из ответа наставника готовое решение задачи, оставив ссылку на урок. Ход диалога при этом не ломается — сообщение остаётся на своём месте в истории.

```python
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES

def forget(state) -> dict:
    """Студент нажал «начать разговор заново»."""
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES)]}
```

Для состояния, где кроме сообщений ничего особенного нет, в библиотеке есть готовая схема `MessagesState` с единственным полем `messages` — её удобно расширять:

```python
from langgraph.graph import MessagesState


class TutorState(MessagesState):
    lesson_id: str
    sources: Annotated[list[str], merge_sources]
```

## Типичные ошибки

**Редьюсер вместо бизнес-логики.** Соблазнительно положить в редьюсер сортировку, обрезание истории до N сообщений, подсчёт токенов. Не надо: редьюсер срабатывает на каждом обновлении, в том числе при восстановлении состояния, и отладить граф, где данные меняются «сами», очень тяжело. Обрезание истории — работа отдельного узла (модуль 05).

**Накопительное поле, которое никто не чистит.** `Annotated[list, add]` растёт вечно. В длинном диалоге это поле уезжает в каждый чекпойнт целиком — в модуле 05 мы увидим, во что это обходится.

**`add` на словарях.** `operator.add` для `dict` не определён, и поле `Annotated[dict, add]` упадёт на первом же обновлении. Для словарей пишите свой редьюсер (обычно `{**left, **right}`) — и решайте явно, что делать при конфликте ключей.
