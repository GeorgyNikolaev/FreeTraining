# Оценка качества: измерять, а не спорить

Тесты из прошлого урока отвечают на вопрос «работает ли граф». Остаётся второй: «хорошо ли он отвечает». Здесь нет `assert`, но есть измерение — и без него любая правка промпта превращается в спор о вкусах.

## Датасет — это просто список случаев

Начинается всё не с инструментов, а с двадцати-тридцати реальных примеров:

```python
examples = [
    {
        "inputs": {"question": "чем редьюсер отличается от маршрутизатора?",
                   "lesson_id": "langgraph/02-graph-and-state/02-reducers"},
        "outputs": {"должен_сослаться_на": "langgraph/02-graph-and-state/02-reducers",
                    "должен_упомянуть": ["объединение значений", "выбор следующего узла"]},
    },
    {
        "inputs": {"question": "напиши за меня диплом", "lesson_id": "..."},
        "outputs": {"должен_отказаться": True},
    },
]
```

Брать их нужно из жизни: настоящие вопросы студентов, настоящие решения ДЗ, включая неудачные. Двадцать реальных случаев полезнее двухсот придуманных, потому что придуманные описывают ваше представление о пользователях, а не пользователей.

Обязательно включите в набор неприятное: вопрос не по теме, вопрос с ошибочной предпосылкой («в LangGraph ведь нет циклов?»), попытку получить готовое решение обходным путём, вопрос про урок, которого нет.

## Три вида проверок

| Вид | Пример для наставника | Чем считать |
|---|---|---|
| Детерминированная | сослался на нужный урок; не выдал решение без спроса; уложился в лимит вызовов | обычный Python |
| Сравнение с эталоном | вердикт по ДЗ совпал с оценкой преподавателя | точность, полнота |
| Судейство моделью | ответ опирается на текст урока и не противоречит ему | вызов модели с рубрикой |

Первая строка — самая недооценённая. Огромную часть качества наставника можно измерить без всякой модели: сослался ли на урок, который действительно существует; не показал ли решение, когда не разрешали; не ушёл ли за лимит вызовов. Это дёшево, стабильно и не требует судьи.

## Модель как судья

Там, где нужен именно смысл, оценку делает отдельный вызов модели со строгой рубрикой:

```python
class Verdict(BaseModel):
    """Оценка ответа наставника."""
    grounded: bool = Field(description="Ответ опирается на текст урока и не противоречит ему")
    no_spoiler: bool = Field(description="Ответ не содержит готового решения задачи")
    comment: str


judge = judge_model.with_structured_output(Verdict)


def evaluate_answer(lesson_text: str, question: str, answer: str) -> Verdict:
    return judge.invoke(
        f"<урок>{lesson_text}</урок>\n<вопрос>{question}</вопрос>\n<ответ>{answer}</ответ>\n"
        "Оцени строго по критериям. Если сомневаешься — ставь False."
    )
```

Что делает судью пригодным:

- **Бинарные критерии вместо оценки от 1 до 10.** «Опирается ли на урок: да/нет» воспроизводимо; «оцени качество на 7» — нет.
- **Отдельный вызов на критерий**, если критериев много, — та же логика, что у веера проверки ДЗ.
- **Материал под рукой.** Судья должен видеть текст урока, иначе он оценивает правдоподобие, а не правильность.
- **Проверка самого судьи.** Разметьте два десятка случаев руками и посмотрите, насколько судья с вами согласен. Судья, который расходится с вами в трети случаев, не измеряет ничего.

## Проверка проверяющего

У наставника есть особая задача: он сам оценивает домашние задания. Значит, его оценки надо сверять с эталоном.

Возьмите десять решений — часть верных, часть с типичными ошибками, часть пустых — и разметьте их сами: какие признаки выполнены. Дальше метрика простая: доля признаков, по которым агент согласен с вами. Отдельно считайте два вида промахов, потому что цена у них разная: «не заметил ошибку» (студент уверен, что всё верно) и «придрался к верному решению» (студент правит работающий код). Второе бьёт по доверию сильнее.

## Инструменты

Гонять это можно и обычным скриптом: прогнать граф по случаям, посчитать метрики, сложить в файл, сравнить с прошлым прогоном. Для наставника такого скрипта достаточно.

Если трейсинг уже на LangSmith, там есть и оценка: датасеты хранятся в сервисе, функция `evaluate` прогоняет цель по датасету с набором оценщиков и складывает результаты в эксперимент, который видно рядом с трейсами. Версия пакета `langsmith` на сентябрь 2026 — 0.13.x.

```python
from langsmith import evaluate

evaluate(
    lambda inputs: graph.invoke(inputs, config)["answer"],
    data="наставник-вопросы-по-урокам",
    evaluators=[grounded_evaluator, no_spoiler_evaluator],
    experiment_prefix="промпт-v4",
)
```

Главное не в инструменте, а в правиле: **каждая правка промпта или графа прогоняется по датасету, и результат сравнивается с предыдущим**. Иначе улучшение одного случая тихо ломает пять других — типичная история с промптами.

## Что мерить у наставника

| Метрика | Как считается | Зачем |
|---|---|---|
| Доля ответов со ссылкой на существующий урок | детерминированно | главный признак «не выдумывает» |
| Доля отказов на вопросы не по курсу | детерминированно | классификатор не разъехался |
| Согласие с эталоном по проверке ДЗ | сравнение с разметкой | ради этого наставник и нужен |
| Доля ответов, опирающихся на урок | судья | качество объяснений |
| Средние вызовы модели и токены на ответ | из состояния | стоимость |
| Доля ответов дольше 15 секунд | замер | терпение студента конечно |

## Типичные ошибки

**Датасет из придуманных вопросов.** Показывает, что агент справляется с вашими представлениями о пользователях.

**Оценка «на глаз» после правки промпта.** Три примера, которые вы помните, всегда выглядят лучше. Остальные семнадцать — неизвестно.

**Судья без материала.** Модель, которой не дали текст урока, оценивает складность речи.

**Одно число вместо профиля ошибок.** «Качество 82%» не говорит, что делать. «Не заметил ошибку в 3 случаях из 10» — говорит.

**Оценка в CI на каждый коммит.** Дорого и медленно: прогон по датасету — это десятки настоящих вызовов модели. Место оценки — перед выкаткой изменений в промпты и граф, а не в каждом push.
