# Когда узел падает: повторы, обработчики, таймауты и кеш

В домашнем задании модуля 02 граф падал с `FileNotFoundError` на опечатке в `lesson_id`. Это был честный сбой, и теперь пора решить, что с такими сбоями делать. Возможностей четыре, и путать их не надо: повтор — для временных сбоев, обработчик — для окончательных, таймаут — для зависаний, кеш — для повторных вычислений.

Всё, что ниже, кроме повторов и кеша, появилось в langgraph 1.2 (май 2026) и на сентябрь 2026 работает только в Python-версии.

## Повторы: `retry_policy`

Провайдер моделей вернул 503, сеть моргнула — такие сбои проходят сами. Политика повторов задаётся на узле:

```python
from langgraph.types import RetryPolicy

builder.add_node(
    "answer",
    answer,
    retry_policy=RetryPolicy(
        max_attempts=3,
        initial_interval=0.5,
        backoff_factor=2.0,
        max_interval=8.0,
        jitter=True,
        retry_on=(ConnectionError, TimeoutError),
    ),
)
```

| Параметр | Что задаёт |
|---|---|
| `max_attempts` | сколько всего попыток, включая первую |
| `initial_interval` | пауза перед первым повтором, секунды |
| `backoff_factor` | во сколько раз растёт пауза с каждой попыткой |
| `max_interval` | потолок паузы |
| `jitter` | добавлять случайный разброс, чтобы повторы не били в одну секунду |
| `retry_on` | какие исключения считать временными |

`retry_on` — самый важный параметр. Повторять `FileNotFoundError` бессмысленно: файла не станет больше от третьей попытки, а студент подождёт лишние секунды. Повторяйте только то, что действительно бывает временным.

Требование к узлу с повторами: он должен быть безопасен при повторном выполнении. Узел, который сначала списывает токены со счёта студента, а потом падает, при повторе спишет их дважды.

## Обработчик ошибки: `error_handler`

Повторы кончились, а узел всё равно упал. Без обработчика падает весь запуск. С обработчиком — вы получаете возможность вернуть состояние в осмысленный вид:

```python
from langgraph.errors import NodeError
from langgraph.types import Command


def on_lesson_error(state: TutorState, error: NodeError) -> Command:
    return Command(
        update={
            "context": "",
            "answer": "Не удалось открыть текст урока. Отвечу по общим знаниям, "
                      "но советую перепроверить по уроку.",
        },
        goto="answer",
    )


builder.add_node("load_lesson", load_lesson, error_handler=on_lesson_error)
```

Обработчик — это узел: он получает состояние и, если объявить параметр с типом `NodeError`, сведения о сбое. У `NodeError` два поля: `node` — имя упавшего узла и `error` — само исключение. Возвращает обработчик `Command`, то есть может и починить состояние, и увести граф на другую ветку.

Порядок такой: сначала исчерпываются повторы, и только потом вызывается обработчик. Проверено на langgraph 1.2.11: с `max_attempts=3` обработчик увидел ошибку третьей попытки.

Если падает сам обработчик, запуск падает — второго круга защиты нет.

Политику можно задать сразу для всех узлов:

```python
builder.set_node_defaults(
    retry_policy=RetryPolicy(max_attempts=3),
    error_handler=on_any_error,
)
```

Умолчания перекрываются параметрами конкретного узла. Одна тонкость: повторы и таймауты распространяются и на узлы-обработчики, а кеш — нет.

## Таймауты: только для асинхронных узлов

```python
builder.add_node("answer", answer, timeout=30)
```

При превышении узел падает с понятным сообщением:

```
langgraph.errors.NodeTimeoutError: Node 'answer' exceeded its run timeout of 30.000s
```

Важное ограничение, на которое напарываются все: **таймаут работает только с асинхронными узлами**. Синхронный узел при попытке задать таймаут даёт ошибку ещё до запуска:

```
ValueError: Node timeouts are only supported for async nodes because sync Python
execution cannot be safely cancelled in-process. Node 'answer' is sync.
```

Причина честная: прервать выполняющуюся синхронную функцию в том же процессе нельзя безопасно. Практический вывод: если у вас есть узлы, которые ходят в сеть, пишите их через `async def` — это не вопрос производительности, а вопрос управляемости.

Кроме числа секунд, `timeout` принимает `TimeoutPolicy` с двумя видами ограничений: `run_timeout` — общее время работы узла, `idle_timeout` — время без признаков жизни (полезно для узлов, которые стримят: пока токены идут, узел жив).

Таймаут хорошо сочетается с обработчиком: `NodeTimeoutError` приходит в `error_handler` как обычная ошибка, и вместо падения студент получает «модель думает слишком долго, попробуйте переформулировать».

## Кеш: `cache_policy`

Узел, который читает текст урока, при каждом вопросе читает один и тот же файл. Узел, который классифицирует вопрос, при повторе того же вопроса даёт тот же ответ. Такие узлы кешируются:

```python
from langgraph.types import CachePolicy
from langgraph.cache.memory import InMemoryCache

builder.add_node("load_lesson", load_lesson, cache_policy=CachePolicy(ttl=300))
graph = builder.compile(cache=InMemoryCache())
```

Ключ кеша по умолчанию считается по входу узла; своя функция задаётся параметром `key_func`. Кеш надо включить при компиляции — без `cache=` политика ничего не делает. Проверено: второй вызов графа с тем же входом не выполняет тело узла вовсе.

`InMemoryCache` живёт в процессе и умирает вместе с ним — для разработки этого достаточно, для прода в библиотеке есть реализации на внешних хранилищах.

Кеш экономит деньги, но добавляет класс багов «почему он отвечает старым»: `ttl` держите коротким и помните, что кешируется узел целиком, включая случайность в ответе модели.

## Что из этого нужно наставнику

| Узел | Что ставим | Почему |
|---|---|---|
| `load_lesson` | `error_handler`, кеш с `ttl=300` | файла может не быть — это не временный сбой; содержимое меняется редко |
| `classify`, `answer`, `review` | `retry_policy` с `retry_on` для сетевых ошибок, `timeout` (асинхронные узлы) | провайдер моделей моргает и иногда думает слишком долго |
| узлы веера проверки ДЗ | `retry_policy`, обработчик, отмечающий признак как «не проверен» | один упавший признак не должен ронять проверку целиком |

## Типичные ошибки

**`retry_on` по умолчанию.** Политика без `retry_on` повторяет всё подряд, включая ошибки в вашем коде. `KeyError` из-за опечатки будет честно повторён три раза — и только потом упадёт.

**Обработчик, который прячет проблему.** `error_handler`, возвращающий «всё хорошо», превращает сбой в тихую деградацию: студент получает ответ без урока и не знает об этом. Обработчик должен либо чинить, либо явно сообщать, что результат неполный.

**Таймаут на синхронном узле.** Не забудется: он падает сразу и с внятным текстом. Но переписывание узла в `async` тянет за собой асинхронный вызов модели и асинхронное чтение файла — лучше заложить это сразу.

**Кеш на узле с побочным эффектом.** Узел, который пишет в базу и кешируется, при попадании в кеш в базу не напишет. Кешировать можно только чистые вычисления.
