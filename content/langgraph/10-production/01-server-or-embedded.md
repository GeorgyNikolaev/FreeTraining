# Сервер LangGraph или ваш собственный?

В модуле 07 наставник уже работает внутри платформы: граф вызывается из FastAPI, поток идёт по SSE, состояние лежит в Postgres. Возникает законный вопрос — зачем тогда отдельный сервер LangGraph, про который говорят в документации?

Ответ зависит от того, что вам нужно сверх вызова графа.

## Что даёт сервер, чего нет у библиотеки

Сервер — это готовое приложение вокруг ваших графов: HTTP-API для запусков, хранилище нитей, очередь фоновых задач, планировщик по расписанию, версии конфигураций.

| Возможность | Библиотека в вашем приложении | Сервер LangGraph |
|---|---|---|
| Вызвать граф, получить поток | да, сами | да, из коробки |
| Хранить нити и снимки | да, сами (чекпойнтер) | да |
| Фоновый запуск, не привязанный к HTTP-запросу | пишете сами (очередь, воркер) | да |
| Запуск по расписанию | пишете сами | да, планировщик |
| Несколько конфигураций одного графа с версиями | пишете сами | ассистенты |
| Отмена запуска, дожидание, подключение к идущему потоку | пишете сами | да |
| Авторизация под вашу модель прав | ваша, уже есть | своя, настраивается отдельно |

Смысл таблицы: сервер экономит работу там, где у вас **нет** готового приложения. У платформы FreeTraining оно есть — с авторизацией, базой, фронтендом и деплоем. Тащить рядом второй сервер, чтобы вызывать граф, — лишний слой, вторая система прав и ещё один процесс на мониторинге.

**Рекомендация для нашего случая:** граф остаётся библиотекой внутри FastAPI. Сервер оправдан, когда появится очередь фоновых прогонов, которую не хочется писать самому, — и даже тогда его можно поставить рядом, только под фоновые задачи.

Это тот случай, когда официальная документация подталкивает к одному решению (она про платформу), а трезвый выбор часто другой.

## Локальный сервер полезен всегда

Независимо от продакшена, локальный сервер стоит держать — ради Studio, в которой видно граф, состояние и шаги. Настройка — тот же `langgraph.json` из модуля 01:

```json
{
  "dependencies": ["."],
  "graphs": {
    "tutor": "./tutor/graph.py:graph",
    "audit": "./tutor/audit.py:audit_course"
  },
  "env": "./.env"
}
```

Команды CLI (версия 0.4.x на сентябрь 2026):

| Команда | Что делает |
|---|---|
| `langgraph dev` | локальный сервер в памяти + ссылка на Studio |
| `langgraph validate` | проверяет `langgraph.json` |
| `langgraph build` | собирает образ Docker с сервером и вашими графами |
| `langgraph up` | поднимает сервер в контейнере |
| `langgraph dockerfile` | генерирует Dockerfile, если нужен свой процесс сборки |
| `langgraph new` | новый проект из шаблона |
| `langgraph deploy` | деплой в облачный сервис (в статусе беты) |

Файл конфигурации умеет больше перечисленного в модуле 01: `python_version`, `dockerfile_lines` для системных зависимостей, `http` для настройки приложения, `store` для конфигурации хранилища (включая индекс семантического поиска) и `auth` для подключения своей авторизации.

## Ассистенты: конфигурация как данные

Одно понятие сервера стоит знать, даже если сервер вы не берёте, — **ассистент**. Это граф плюс конфигурация: промпт, модель, значения контекста. Один и тот же граф наставника может существовать как «строгий наставник» и «подсказчик», как «для новичков» и «для продвинутых» — без единой правки кода.

У ассистентов есть версии: конфигурацию меняют, прогоняют по датасету (модуль 09) и переключают рабочую версию, а при плохом результате возвращают предыдущую.

Если сервер не используется, идею всё равно стоит забрать: держите конфигурацию отдельно от кода — в таблице или файле, с версией и возможностью откатиться. Тогда правка промпта перестаёт быть деплоем.

## Варианты размещения

| Вариант | Что это | Когда |
|---|---|---|
| Библиотека в своём приложении | как у нас: `pip install langgraph` и вызов графа | есть своё приложение |
| Свой сервер из образа | `langgraph build` и запуск контейнера у себя | нужны фоновые прогоны и API, данные не выходят наружу |
| Облачный сервис LangSmith Deployment | размещение у поставщика | нет своей инфраструктуры и нет ограничений на размещение данных |

У платных вариантов тарифы меняются — проверяйте перед выбором. И помните про данные: вопросы студентов и их решения — это пользовательский контент, а размещение у внешнего поставщика означает, что он туда попадёт.

## Типичные ошибки

**Сервер «потому что так в документации».** Второй процесс, вторая система прав, второй деплой — ради вызова, который уже работает из вашего приложения.

**Отказ от локального сервера.** Studio стоит почти ничего и экономит часы отладки: увидеть граф картинкой обычно быстрее, чем читать `draw_mermaid()`.

**Промпты, зашитые в код.** Каждая правка формулировки — релиз. Конфигурацию наставника (промпты, модель, лимиты) выносите наружу, даже если ассистентов у вас нет.

**Забытый `langgraph validate`.** Ошибка в `langgraph.json` обнаруживается при старте сервера, а не при сборке образа.
