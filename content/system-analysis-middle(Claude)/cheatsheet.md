# Шпаргалка системного аналитика

## Границы системы

Функция остаётся снаружи, если верно хотя бы одно из первых двух:

1. Источник истины по данным — чужая система (сильнейший признак).
2. За ошибку отвечает другое подразделение.
3. Правило меняет не наш заказчик.
4. Функция меняется реже раза в год и есть промышленный сервис.

Список «вне границ»: каждая строка = «мы не делаем X» + «делает Y».
Каналы вывода данных (выгрузки, печать, реплика для аналитиков) описываются
наравне с интеграциями.

## Уровни требований

| Уровень | Отвечает на | Пример |
| --- | --- | --- |
| Бизнес | Зачем | Срок решения 2 рабочих дня к концу года |
| Пользовательский | Что делает человек | Менеджер отправляет заявку без звонка |
| Системный | Что делает система | При `submit` запрос в два БКИ, таймаут 5 с |

Требование → ссылается на правило, а не дублирует его значение.
Идентификаторы: `BR-`, `UR-`, `SR-`, `NFR-`, `BRULE-`. Номера не переиспользуются.

## Критерии приёмки

```gherkin
Дано: <состояние системы и данные с конкретными значениями>
Когда: <действие конкретной роли>
Тогда: <наблюдаемый результат: статус, код, запись в журнале>
```

Запрещено: «корректно», «правильно», расположение элементов, внутренние поля БД.
На каждый шаг — три негативных группы: нарушение предусловий, отказ смежной
системы, действие без прав.

## Бизнес-правила

Поля каталога: ID, формулировка, источник, владелец, дата вступления, версия.
Типы: факт, ограничение, вычисление, вывод, реакция.
Полнота таблицы решений: произведение числа значений условий = числу строк;
строки с одинаковыми условиями и разным результатом = противоречие.
Объект хранит `rules_version` на момент фиксации.

## Нефункциональные требования

Шаблон: **при [нагрузке и условиях] метрика [название] не хуже [значения];
при нарушении [последствие]**.

| Категория | Что указать |
| --- | --- |
| Производительность | p95/p99, не среднее; число одновременных пользователей |
| Пропускная способность | Операций в день и в пиковый час |
| Доступность | Доля и окно (например, 99,5% в 08:00–20:00 по рабочим дням) |
| Сохранность | RPO и RTO |
| Безопасность | Проверяемое ограничение + журналирование + срок хранения |
| Наблюдаемость | Время до диагноза и без каких данных |
| Совместимость | Квота запросов к смежной системе |

Доступность синхронной цепочки = произведение доступностей: 0,995⁴ ≈ 98,0%.

Таблица деградации: для каждой зависимости — поведение при отказе и что видит
пользователь.

## Состояния

Состояние — свойство объекта, не место в очереди и не исполнитель.
Таблица переходов: из, событие, условие, в, инициатор, эффект.
Отдельно: запрещённые переходы с кодом ответа и права на редактирование полей в
каждом состоянии.

## HTTP-коды

| Код | Когда |
| --- | --- |
| 201 | Создан ресурс, `Location` обязателен |
| 202 | Принято, результат позже; нужен способ узнать результат |
| 400 | Синтаксис запроса |
| 401 | Не аутентифицирован |
| 403 | Нет прав, факт существования объекта не секрет |
| 404 | Нет объекта **или** объект не должен быть виден этому пользователю |
| 409 | Не то состояние |
| 422 | Данные нарушают бизнес-правило |
| 429 | Лимит, обязателен `Retry-After` |

Чувствительные идентификаторы (ИНН, телефон, ФИО) — не в query-строке: поиск
через `POST /…/search`.

## Идемпотентность и конкуренция

| Ситуация | Решение | Параметры |
| --- | --- | --- |
| Повтор создающей операции | `Idempotency-Key` | Хранение 24 ч; совпал ключ и тело → прежний ответ; ключ тот же, тело другое → 409 |
| Повтор вызова смежной системы | Детерминированный ключ `{object}-{action}-{n}` | Переживает перезапуск сервиса |
| Редкие конфликты правки | `ETag` + `If-Match` → 412 | В ответе отдать актуальную версию |
| Долгая работа человека | Пессимистическая блокировка | Срок, продление, принудительное снятие с журналированием |

Повторять автоматически: таймауты, 5xx, 429. Не повторять: 4xx.
Задержки повторов — с разбросом: 1, 5, 25, 125, 625 с.

## Выбор способа обмена

| Вопрос | Да → синхронно | Нет → асинхронно |
| --- | --- | --- |
| Результат нужен пользователю сейчас? | ✓ | |
| Допустима задержка в минуты? | | ✓ |
| Отказ должен блокировать работу? | ✓ | |
| Объём — пакеты и потоки? | | ✓ |

В событии — только идентификаторы, тип, время, `schema_version`. Персональные
данные и банковская тайна в сообщения не кладутся: брокер не проверяет права.
Outbox обязателен там, где событие должно соответствовать изменению данных.
Гарантия «хотя бы один раз» → потребитель идемпотентен. Порядок — только внутри
ключа партиционирования.

## Сверка

Шесть пунктов регламента: что сверяем, период, ключ сопоставления, что считается
расхождением, кто разбирает, срок разбора. Сверять поимённо по ключу, не по
количеству. Легальные расхождения описываются как ожидаемые.

## Данные

| Класс | Следствия |
| --- | --- |
| Открытые | Без ограничений |
| Внутренние | Доступ по роли |
| Персональные данные | Минимизация, маскирование, журнал, срок хранения, основание |
| Банковская тайна | Доступ по служебной необходимости, журнал, запрет в логах и выгрузках |
| Секреты | Только в хранилище секретов |

Классифицируются наборы, покидающие систему: экран, ответ API, выгрузка, событие.
Снимком хранятся: входные данные решения, условия сделки, значения справочников.
Ссылкой — то, чем владеет чужая система.
Мягкое удаление ≠ удаление персональных данных.

## Доступ

Право = субъект + объект + действие + условие.
Роли задают операции, атрибуты — область видимости: отделение, назначение,
авторство, срок.
Матрицу строят от операций, а не от ролей.
Матрица несовместимости: подготовка и решение; изменение правил и решения;
администрирование и аудит; управление правами и любая роль в системе.
Экстренный доступ: причина, срок, журнал, уведомление ИБ, без доступа к журналу.

## Ограничение полей

| Способ | Когда |
| --- | --- |
| Скрытие | Поле не нужно для задачи |
| Маскирование | Нужно сверить, но не использовать; маска постоянна |
| Агрегирование | Нужен уровень, не детали; следить за малыми выборками |
| Токенизация | Нужно сопоставлять, не зная значения |

Маскирование — на сервере. Экспорт проектируется отдельно и беднее экрана.
Тестовые среды — синтетика, не копия промышленной базы.

## Журнал доступа

Поля: `occurred_at`, `actor_id`, `actor_role`, `action`, `object_type`,
`object_id`, `data_scope`, `access_reason`, `result`, `request_id`.
Никаких значений данных. Только добавление и чтение, отдельное хранилище.
Логируются: чтение чувствительных данных, отказы, экспорт (с фильтрами и числом
строк), поиск, изменение прав, экстренный доступ, действия под замещением.

## Постановка задачи: обязательные разделы

Зачем · Область и что не входит · Сценарий с альтернативами · Ссылки на правила ·
Данные и миграция · Контракт и коды ошибок · Права и область видимости ·
Деградация · Критерии приёмки · Метрики после релиза.

DoR: критерии приёмки есть, права названы, поведение при отказах описано,
тестовые данные указаны, открытых вопросов к бизнесу нет.

Декомпозиция — вертикальными срезами: от экрана до данных, каждый срез можно
показать и остановить.

## Приёмка: пять обязательных негативных проверок

1. Чужой объект по прямой ссылке к API.
2. Операция ролью, которой она не положена.
3. Совмещение несовместимых полномочий.
4. Сравнение ответа API с матрицей полей по ролям.
5. Записи в журнале при успешном и при отклонённом обращении.

## Запуск

Стратегии: одномоментно · пилот · параллельная работа · поэтапно по функциям.
Незавершённые объекты: не переносить, доводить в старом процессе, дата закрытия
обязательна.
Критерии выхода из пилота — числами, до его начала.
План отката — с указанием момента, после которого откат невозможен.
Аварийный режим — инструкция вне системы.

## Изменение требований

| Тип | Кто решает |
| --- | --- |
| Уточнение | Аналитик |
| Изменение правила | Владелец правила |
| Новое требование | Заказчик, со сроками |
| Изменение ограничения | Исполняется, сроки пересматриваются |

Для каждого изменения: что меняется, на что влияет, что делать с объектами в
работе. Принятые отклонения — в протокол с датой устранения.
