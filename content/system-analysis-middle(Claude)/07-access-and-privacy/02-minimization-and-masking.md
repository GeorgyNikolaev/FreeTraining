# Минимизация данных и маскирование

Право открыть заявку не означает право видеть всё, что в ней лежит. Разделение
на уровне полей — то место, где требования конфиденциальности перестают быть
декларацией и превращаются в конкретные решения по каждому экрану и каждому
ответу API.

## Минимизация начинается с задачи

Для каждого экрана формулируется задача пользователя, и под неё подбирается
состав полей. Обратный порядок — «покажем всё, что есть, вдруг понадобится» —
даёт экран, который невозможно защитить и по которому нельзя объяснить проверке,
зачем сотруднику эти данные.

Рабочий вопрос к каждому полю: какое решение пользователь примет по-другому,
если этого поля не будет. Нет ответа — поле убирается.

## Четыре способа ограничить поле

| Способ | Что видит пользователь | Когда применять | Ограничение |
| --- | --- | --- | --- |
| Скрытие | Ничего, поля нет в ответе | Данные не нужны для задачи | Пользователь не знает о существовании данных |
| Маскирование | Часть значения: `•••• 4312` | Нужно сверить или подтвердить, но не использовать целиком | Маска не должна позволять восстановить значение перебором |
| Агрегирование | Производный показатель вместо исходных данных | Нужен факт или уровень, не детали | Агрегат по малой выборке может раскрыть исходные данные |
| Токенизация | Стабильный суррогат вместо значения | Нужно сопоставлять записи, но не знать значение | Требует хранилища соответствий с отдельным доступом |

Маскирование выполняется на сервере. Ответ API не должен содержать полного
значения, которое интерфейс потом прячет: инструменты разработчика в браузере
открываются в два клика, а трафик пишется в журналы.

Второе правило: маска постоянна. Если один экран показывает последние четыре
цифры, а другой — первые четыре, вместе они раскрывают восемь.

## Особые случаи

**Экспорт.** Файл уходит из-под контроля системы навсегда: к нему не применяются
ни права, ни журнал, ни срок хранения. Поэтому состав полей экспорта
проектируется отдельно и почти всегда беднее экрана.

**Тестовые среды.** Копия промышленной базы в тестовой среде — самый массовый
способ вынести персональные данные за периметр. Замена — генерация синтетики
или необратимое обезличивание с сохранением статистических свойств: длин, форматов,
распределений, связей между таблицами.

**Поиск.** Поиск по фамилии или телефону — это способ узнать, кто есть в базе,
даже без доступа к карточкам. Поиск по чувствительным полям ограничивают ролью,
журналируют и ограничивают по темпу.

## Где ошибаются

- **Маскирование в интерфейсе.** Полное значение в ответе API — это утечка,
  которую не видно на демонстрации.
- **Агрегат по одной записи.** «Средняя сумма кредитов клиентов отделения» при
  одном клиенте — это его сумма.
- **Экспорт «как на экране».** Права экрана экспортом не наследуются: файл живёт
  своей жизнью.
- **Обезличивание удалением ФИО.** Набор из ИНН, суммы, даты и отделения
  идентифицирует клиента не хуже фамилии.

## На конвейере

Состав полей карточки заявки по ролям:

| Поле | Менеджер | Андеррайтер | СБ | Аудитор |
| --- | --- | --- | --- | --- |
| Номер, статус, сумма, срок | Полностью | Полностью | Полностью | Полностью |
| Наименование, ИНН, ОГРН | Полностью | Полностью | Полностью | Полностью |
| ФИО руководителя | Полностью | Полностью | Полностью | Скрыто |
| Телефон руководителя | Полностью | Полностью | Полностью | Скрыто |
| Паспорт руководителя | Маска `•• •• ••4312` | Полностью | Полностью | Скрыто |
| Скоринговый балл | Скрыт | Полностью | Скрыт | Скрыт |
| Отчёт БКИ | Агрегаты: число кредитов, платёж, факт просрочки | Полностью, отдельным запросом | Скрыт | Скрыт |
| Обороты по счетам из АБС | Скрыто | Полностью | Скрыто | Скрыто |
| Стоп-факторы | Скрыты, включая признак наличия | Только факт: проверка не пройдена | Полностью, с причиной | Скрыты |
| Комментарий андеррайтера | Видимая часть | Полностью | Скрыт | Полностью |
| История статусов | Полностью | Полностью | Полностью | Полностью |

Четыре решения, которые стоит перенести в свой проект.

**Аудитор не видит персональные данные.** Аудитор проверяет соблюдение
процедуры: кто, когда, на основании чего принял решение. Для этого ФИО
руководителя клиента не нужны — нужны роли, время, версия правил и полнота
проверок. Это самый частый недочёт: аудитору дают доступ «ко всему», хотя его
задача требует меньше данных, чем задача менеджера.

**Менеджер не видит даже признака наличия стоп-фактора.** Отдельный признак —
уже информация: сопоставив его со статусом, менеджер поймёт причину и может
передать её клиенту. Поэтому скрыт и признак, и связанный с ним код причины
отказа — менеджер видит нейтральную формулировку «отказ по результатам проверки».

**Паспорт маскирован именно для менеджера.** Менеджеру паспорт нужен, чтобы
сверить с оригиналом при подписании: последних четырёх цифр достаточно.
Андеррайтеру он нужен целиком — для проверок по внешним источникам.

**Отчёт БКИ для менеджера сведён к трём агрегатам.** Это решение кредитного
комитета из первого модуля, доведённое до состава полей: число действующих
кредитов, сумма ежемесячных платежей, факт просрочек за 12 месяцев. Названия
банков-кредиторов, суммы и даты — не показываются.

Состав выгрузки — тот же принцип, но жёстче:

| Поле | В выгрузке |
| --- | --- |
| Номер заявки, статус, сумма, срок, дата | Да |
| ИНН, наименование | Да |
| Отделение, ответственный сотрудник | Да |
| ФИО, телефон, паспорт | Нет |
| Балл, отчёт БКИ, стоп-факторы | Нет |
| Причина отказа | Только код, без текстового комментария |

Каждая выгрузка пишется в журнал доступа с числом строк и составом фильтров.
За первый квартал это дало неожиданный результат: 11 сотрудников выгружали весь
список отделения ежедневно. Разбор показал, что им не хватало сортировки по
сроку в интерфейсе, — после доработки экрана число выгрузок упало в двадцать раз.
Это типичная находка: массовый экспорт почти всегда означает, что в интерфейсе
чего-то не хватает, а не что сотрудники злоупотребляют.

Тестовые данные: промышленную базу в тестовую среду не копируют. Генератор
создаёт 50 тысяч заявок с корректными по формату ИНН из тестового диапазона,
синтетическими ФИО и распределением сумм, повторяющим промышленное. Отдельно
поддерживается набор из 40 «эталонных» заявок под каждый сценарий приёмки —
включая заявку клиента из стоп-листа и заявку с отозванным согласием.
