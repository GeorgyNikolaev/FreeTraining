# Приёмка и изменение требований

Приёмка проверяет не то, что система работает, а то, что она делает именно то,
о чём договаривались. Разница видна на негативных сценариях: работающая система,
которая разрешает лишнее, приёмку проходить не должна.

## Кто принимает и что именно

| Принимающий | Что проверяет | Чем подтверждается |
| --- | --- | --- |
| Бизнес-заказчик | Сценарии, сроки, полезность | Протокол с перечнем сценариев и результатом |
| Тестирование | Критерии приёмки, регрессия | Отчёт о прогоне |
| ИБ | Разграничение доступа, журналирование, состав данных | Отчёт проверки по согласованному перечню |
| Внутренний аудит | Контрольные процедуры: четыре глаза, журнал, неизменяемость | Заключение |
| Эксплуатация | Мониторинг, инструкции, восстановление | Чек-лист готовности к поддержке |

Порядок имеет значение: проверку ИБ и аудита планируют до финального демо, а не
после. Замечание аудита на демонстрации означает перенос запуска, потому что
контрольные процедуры меняются не настройкой.

Тест-кейсы не пишутся заново — они выводятся из критериев приёмки. Если из
критерия нельзя получить тест-кейс механически, критерий сформулирован плохо.

## Обязательные негативные проверки внутренних систем

Пять проверок, которые должны быть в любой системе с разграничением доступа:

1. Обращение к чужому объекту по прямой ссылке — не через интерфейс, а запросом
   к API.
2. Выполнение операции ролью, которой она не положена.
3. Совмещение несовместимых полномочий — попытка выполнить оба действия одним
   сотрудником.
4. Присутствие чувствительных полей в ответе API там, где интерфейс их прячет.
5. Появление записей в журнале доступа при успешном и при отклонённом обращении.

Четвёртая проверка выполняется не глазами, а сравнением ответа API с матрицей
полей — иначе её пропускают.

## Изменения после старта разработки

Изменения будут; вопрос в том, проходят они через процедуру или через личную
договорённость.

| Тип | Признак | Кто решает |
| --- | --- | --- |
| Уточнение | Не меняет объём и поведение, снимает неоднозначность | Аналитик |
| Изменение правила | Меняется бизнес-правило при том же сценарии | Владелец правила |
| Новое требование | Появляется сценарий или поле | Заказчик, с пересмотром сроков |
| Изменение ограничения | Меняются требования регулятора или ИБ | Исполняется, сроки пересматриваются |

Для каждого изменения фиксируются три вещи: что меняется, на что влияет (задачи,
тесты, документы, уже созданные данные), что делать с объектами в работе.
Последнее забывают чаще всего, а именно оно порождает вопросы через год.

## Где ошибаются

- **Приёмка по демонстрации.** Демонстрация показывает основной поток на
  подготовленных данных; исключения и права так не проверяются.
- **Тест-кейсы пишутся тестировщиком с нуля.** Это второй перевод требований с
  неизбежными расхождениями.
- **Изменение принимается устно.** Через месяц разработчик и аналитик помнят
  разное, а протокола нет.
- **Нет ответа про уже созданные объекты.** Правило изменилось — а что с
  заявками, поданными вчера?

## На конвейере

Матрица приёмки MVP: 64 сценария, из них 27 негативных. Фрагмент по срезу
«решение андеррайтера»:

| № | Сценарий | Ожидаемо | Кто проверяет |
| --- | --- | --- | --- |
| 4.1 | Решение по назначенной заявке в `manual_review` | 201, статус `approved`, снимок сохранён | Тестирование |
| 4.2 | Решение по заявке из чужой очереди через API | 404, запись в журнале `denied` | ИБ |
| 4.3 | Решение автором заявки | 403 `segregation_violation`, запись в журнале | Аудит |
| 4.4 | Решение по заявке в `approved` | 409 `invalid_state` | Тестирование |
| 4.5 | Сумма решения 60 млн ₽ | 422 `amount_out_of_range` | Тестирование |
| 4.6 | Ответ API менеджеру не содержит `score` и `credit_report` | Поля отсутствуют в JSON | ИБ |
| 4.7 | Просмотр отчёта БКИ андеррайтером | Запись в журнал с `data_scope: credit_report` | ИБ |
| 4.8 | Блокировка истекла, решение принято другим андеррайтером | 201, событие о смене ответственного | Тестирование |
| 4.9 | Решение при недоступной АБС | 201, заявка `approved`, сделка в очереди | Тестирование |

Пункт 4.6 — тот самый, который проходит только при сравнении с матрицей полей.
На первой приёмке он не прошёл: поле `score` присутствовало в ответе со
значением `null` для менеджера, а для руководителя отделения — со значением.

Пример проведённого изменения: в мае риск-подразделение подняло порог
автоматического решения с 5 до 7 млн ₽.

| Вопрос | Ответ |
| --- | --- |
| Тип изменения | Изменение правила `BRULE-4`, владелец — риск |
| Что меняется | Значение настройки, версия правил 2 → 3 |
| Что затрагивает | Таблица решений, 4 тест-кейса, документ каталога правил, отчётность по доле автоматических решений |
| Разработка | Не требуется: порог вынесен в настройку ещё в первом релизе |
| Объекты в работе | Заявки в статусе `submitted` и `checks_running` на момент изменения дорабатываются по версии 2 |
| Как проверено | Заявка на 6 млн ₽, поданная до изменения, ушла в `manual_review`; поданная после — одобрена автоматически |
| Срок | 1 день, из них полдня — согласование с комплаенсом |

Изменение заняло день только потому, что решение вынести порог в настройку было
принято на этапе требований. Если бы порог был в коде, тот же результат стоил бы
релиза: разработка, тестирование, регрессия, окно установки — две недели.

Последняя строка протокола приёмки, которую стоит копировать в любой проект:
перечень принятых отклонений. Из 64 сценариев два были приняты с оговоркой —
возврат на доработку не уведомляет менеджера письмом (только в интерфейсе) и
сверка не различает легальную корректировку суммы операционистом. Оба записаны
с датой устранения. Отклонение, принятое без записи, через месяц перестаёт
считаться отклонением и становится нормой.
