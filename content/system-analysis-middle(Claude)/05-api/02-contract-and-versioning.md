# Контракт: схемы, ошибки, пагинация, версионирование

Контракт — это то, что нельзя изменить в одностороннем порядке. Всё остальное в
API можно. Поэтому в контракт входит меньше, чем кажется, и каждый пункт стоит
осознанного решения.

## Что фиксирует контракт

| Элемент | Фиксируется | Не фиксируется |
| --- | --- | --- |
| Поля ответа | Имена, типы, обязательность, формат | Порядок полей в JSON |
| Значения перечислений | Полный список и смысл каждого | Внутреннее числовое представление |
| Коды ошибок | Машиночитаемый код и условие | Текст сообщения |
| Пагинация | Способ и параметры | Размер страницы по умолчанию |
| Лимиты | Максимальный размер тела, частота запросов | Реализация ограничителя |

Формат ошибки — один на всё API. Разумный ориентир — RFC 9457 (Problem Details
for HTTP APIs, опубликован в 2023 году, заменил RFC 7807): поля `type`, `title`,
`status`, `detail`, `instance` плюс собственные поля. Главное — машиночитаемый
код и, если ошибка связана с конкретным полем, указание на поле.

```json
{
  "type": "https://api.bank.ru/errors/consent-required",
  "title": "Не приложено согласие на запрос кредитной истории",
  "status": 422,
  "code": "consent_required",
  "instance": "/applications/9c2f.../submit",
  "errors": [{ "field": "documents", "code": "missing_document_type", "value": "bki_consent" }]
}
```

В `detail` и `title` не должно быть персональных данных: тексты ошибок попадают
в логи клиента, в системы мониторинга и в скриншоты обращений в поддержку.

## Пагинация

| Способ | Как работает | Когда выбирать | Чем плох |
| --- | --- | --- | --- |
| Offset | `?limit=50&offset=100` | Небольшие наборы, нужна навигация по номерам страниц | При вставках записи сдвигаются: пользователь видит дубли и пропуски; на больших смещениях медленно |
| Keyset (курсор) | `?limit=50&cursor=...` | Списки, которые пополняются в реальном времени; большие объёмы | Нельзя прыгнуть на страницу N |

Для рабочих очередей — очереди андеррайтеров, ленты событий — keyset
предпочтительнее: пока сотрудник листает, в очередь падают новые заявки, и
offset даёт повторы. Курсор при этом непрозрачен для клиента и не должен
содержать данных: его декодируют и пробуют подменить чаще, чем кажется.

## Версионирование

Ломающее изменение — то, после которого существующий клиент перестаёт работать
без правок.

| Изменение | Ломающее |
| --- | --- |
| Добавлено необязательное поле в ответ | Нет |
| Добавлено обязательное поле в запрос | Да |
| Поле удалено или переименовано | Да |
| Добавлено значение в перечисление | Да, если клиент не готов к неизвестным значениям |
| Тип поля изменён со строки на число | Да |
| Расширен диапазон допустимых значений | Нет |
| Ошибка стала возвращаться с другим кодом | Да |

Строка про перечисления — самая коварная. Новый статус заявки для клиента,
написанного по старому контракту, означает падение или отображение пустоты.
Поэтому правило «клиент обязан игнорировать неизвестные значения» фиксируется в
контракте заранее, до первого расширения.

Во внутренней системе с известными потребителями версионирование обычно
ограничивается версией в пути (`/v1/applications`) плюс политикой: поддерживаем
две версии, старая живёт 6 месяцев после выхода новой. Согласовывать это нужно
до первого потребителя, а не в момент, когда понадобилось ломающее изменение.

## Где ошибаются

- **Персональные данные в query-строке.** Параметры попадают в логи прокси,
  историю браузера и трассировки; для поиска по чувствительным идентификаторам
  используется POST с телом.
- **Контракт пишется после реализации.** Тогда он описывает то, что получилось,
  включая случайности вроде `null` вместо пустого массива.
- **Одно поле с разным смыслом в разных ручках.** `status` заявки и `status`
  проверки с пересекающимися значениями гарантируют ошибку интеграции.
- **Нет ограничений на размер.** Отсутствие лимита на число документов и объём
  тела превращается в отказ в обслуживании при первой же массовой загрузке.

## На конвейере

Фрагмент спецификации создания заявки:

```yaml
paths:
  /v1/applications:
    post:
      summary: Создать черновик заявки
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [inn, amount_minor, term_months, branch_code]
              properties:
                inn:
                  type: string
                  pattern: '^([0-9]{10}|[0-9]{12})$'
                amount_minor:
                  type: integer
                  format: int64
                  minimum: 50000000
                  maximum: 5000000000000
                term_months:
                  type: integer
                  minimum: 6
                  maximum: 60
                branch_code:
                  type: string
      responses:
        '201':
          description: Черновик создан
          headers:
            Location: { schema: { type: string } }
        '422':
          description: Нарушено бизнес-правило
        '403':
          description: Отделение не соответствует отделению сотрудника
```

Обратите внимание на `amount_minor`: минимум 50 000 000 копеек — это 500 тыс. ₽,
максимум 5 000 000 000 000 копеек — 50 млн ₽. Границы продукта попали в схему, и
это осознанный выбор: проверка формата отсекает грубые ошибки сразу. Но сами
пороги продукта остаются в бизнес-правилах — в схеме зафиксированы только
абсолютные границы, которые не меняются вместе с продуктовой политикой.

Таблица кодов ошибок «Конвейера» — единая для всех ручек:

| Код | HTTP | Условие | Что делать клиенту |
| --- | --- | --- | --- |
| `consent_required` | 422 | Нет документа типа `bki_consent` | Приложить согласие и повторить |
| `invalid_state` | 409 | Операция не разрешена в текущем статусе | Обновить карточку, показать актуальный статус |
| `segregation_violation` | 403 | Решение принимает участник подготовки заявки | Передать заявку другому андеррайтеру |
| `branch_scope_violation` | 403 | Отделение сотрудника не совпадает с отделением заявки | Действие невозможно |
| `amount_out_of_range` | 422 | Сумма вне границ продукта | Исправить сумму |
| `duplicate_request` | 409 | Повтор с тем же `Idempotency-Key` и другим телом | Исправить тело или сменить ключ |
| `dependency_unavailable` | 503 | Недоступна смежная система при синхронной операции | Повторить по `Retry-After` |
| `rate_limited` | 429 | Превышен лимит запросов | Повторить по `Retry-After` |

Строка `branch_scope_violation` существует только для операций записи. При
чтении чужой заявки, как решено в прошлом уроке, возвращается 404: сообщать о
существовании объекта нельзя даже кодом ошибки.
