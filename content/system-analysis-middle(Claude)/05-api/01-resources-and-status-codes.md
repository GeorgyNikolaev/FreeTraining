# Ресурсы, методы и коды ответов

Аналитик проектирует API не вместо разработчика, а вместе с ним: состав
ресурсов, правила доступа и коды ошибок — это предметные решения, а не
технические. Ошибка здесь стоит дорого, потому что контракт переживает три
переписывания интерфейса.

## Ресурс — существительное, действие — метод

Базовая дисциплина: путь называет вещь, метод называет действие над ней.
`/applications`, `/applications/{id}/documents`, `/decisions`. Глаголы в пути
(`/getApplicationList`) убивают предсказуемость: клиенту приходится заучивать
каждый вызов отдельно.

Проблема начинается там, где действие не сводится к созданию, чтению,
изменению или удалению: отправить заявку на проверку, принять решение, вернуть
на доработку. Вариантов три.

| Подход | Как выглядит | Когда подходит |
| --- | --- | --- |
| Изменение поля состояния | `PATCH /applications/{id}` с `status` | Переход без побочных эффектов и без дополнительных данных — на практике почти не встречается |
| Подресурс-команда | `POST /applications/{id}/submit` | Переход с эффектами: запуск проверок, уведомления, блокировка полей |
| Отдельный ресурс результата | `POST /applications/{id}/decisions` | Действие порождает объект со своей историей: решение, проверка, платёж |

Правило выбора: если у действия есть автор, время и последствия, которые нужно
хранить, оно порождает ресурс. Решение по заявке — ресурс, а не изменение поля;
именно поэтому в модели данных оно отдельная сущность.

## Коды ответов

| Код | Когда | Частая ошибка |
| --- | --- | --- |
| 200 | Успешное чтение или изменение с телом ответа | Возврат 200 с телом `{"error": ...}` — клиент не отличит успех от ошибки |
| 201 | Создан ресурс; в заголовке `Location` — его адрес | Возвращают 200 и заставляют клиента гадать идентификатор |
| 202 | Запрос принят, результат будет позже | Используют, не дав клиенту способа узнать результат |
| 204 | Успех без тела | Возвращают 204 там, где клиенту нужно новое состояние |
| 400 | Запрос синтаксически неверен | Используют как универсальный код для любой ошибки |
| 401 | Не аутентифицирован | Путают с 403 |
| 403 | Аутентифицирован, но нет прав | Отдают вместе с подробностями объекта |
| 404 | Объект не существует **или не должен быть виден** | Отдают 403 там, где само существование объекта — чувствительная информация |
| 409 | Состояние объекта не допускает операцию | Отдают 400, и клиент не может отличить «данные плохие» от «момент неподходящий» |
| 422 | Данные синтаксически корректны, но нарушают бизнес-правило | Смешивают с 409 |
| 429 | Превышен лимит запросов | Не указывают `Retry-After` |

Разница между 403 и 404 — предметная, а не техническая. 403 сообщает «объект
есть, но он не ваш». В системе, где само существование заявки по конкретному
ИНН — чувствительная информация, такой ответ становится каналом утечки: перебрав
идентификаторы, можно узнать, кто обращался за кредитом. Поэтому для объектов вне
зоны видимости пользователя отдают 404.

Разница между 409 и 422 проще: 409 — «не то состояние» (заявка уже отправлена),
422 — «не те данные» (сумма выше максимума продукта). Клиент по коду понимает,
менять ему данные или дождаться другого состояния.

## Где ошибаются

- **Код ошибки только в тексте сообщения.** Клиент вынужден разбирать строку;
  при изменении формулировки ломается обработка. Машиночитаемый код обязателен.
- **Разные коды для одной ситуации в разных ручках.** Возникает, когда контракт
  описывают по частям разные люди без общей таблицы.
- **Перечисление всех возможных ошибок в документации без указания причин.**
  Клиенту нужен ответ на вопрос «что делать», а не список.

## На конвейере

| Операция | Метод и путь | Коды | Кто вызывает |
| --- | --- | --- | --- |
| Список заявок отделения | `GET /applications?branch=M-12&status=manual_review` | 200, 403 | Менеджер, андеррайтер |
| Карточка заявки | `GET /applications/{id}` | 200, 404 | Менеджер, андеррайтер, СБ |
| Создать заявку | `POST /applications` | 201, 422 | Менеджер |
| Изменить черновик | `PATCH /applications/{id}` | 200, 409, 422 | Менеджер-автор |
| Приложить документ | `POST /applications/{id}/documents` | 201, 409, 413, 422 | Менеджер |
| Отправить на проверку | `POST /applications/{id}/submit` | 202, 409, 422 | Менеджер-автор |
| Принять решение | `POST /applications/{id}/decisions` | 201, 403, 409, 422 | Андеррайтер |
| Вернуть на доработку | `POST /applications/{id}/decisions` с `type=rework` | 201, 403, 409 | Андеррайтер |
| Результат проверки СБ | `POST /applications/{id}/checks/{check_id}/result` | 200, 403, 409 | Сотрудник СБ |
| Отчёт БКИ | `GET /applications/{id}/credit-report` | 200, 403, 404 | Андеррайтер |
| Поиск по ИНН | `POST /applications/search` | 200, 403 | Менеджер, андеррайтер |

Четыре решения из этой таблицы объясняют больше, чем сама таблица.

**`POST /applications/{id}/submit` отдаёт 202, а не 200.** Проверки в БКИ,
скоринге и ПОД/ФТ занимают до двух минут, и ждать их синхронно клиент не должен.
Вместе с 202 возвращается тело со статусом `checks_running` и ссылкой на
`GET /applications/{id}` — способ узнать результат обязателен, иначе 202
бесполезен.

**Отчёт БКИ вынесен в отдельный ресурс.** Если бы он входил в карточку, каждый
её просмотр означал бы доступ к банковской тайне и попадал бы в журнал доступа.
Отдельный путь даёт отдельное право, отдельную запись в журнале и возможность
показать карточку менеджеру без отчёта.

**Поиск по ИНН — `POST`, а не `GET` с параметром.** ИНН — это сведения о том, кто
обращался в банк; в query-строке он попадёт в логи веб-сервера, историю браузера,
трассировки и заголовок `Referer`. Тело POST-запроса в логи не пишется. Это
единственное оправданное отступление от «поиск — это GET», и оно возникает в
любой системе с чувствительными идентификаторами.

**Чужая заявка — 404, а не 403.** Менеджер отделения М-12, запросивший заявку
отделения М-07, получает 404 и не узнаёт о её существовании. Событие при этом
пишется в журнал доступа с результатом `denied` — сотрудник не видит отказа, а
ИБ видит попытку.
