# История, неизменяемость и два разных журнала

Через год после выдачи кредита приходит вопрос: почему по этой заявке приняли
положительное решение. Ответ «потому что балл был 640» не принимается, если
сегодня балл 480, а данные о выручке изменились. Система должна уметь показать
не текущее состояние, а то, которое было в момент решения.

## Что хранить снимком, а что ссылкой

| Тип данных | Как хранить | Почему |
| --- | --- | --- |
| Входные данные решения | Снимок на момент решения | Источник мог измениться, решение обязано быть объяснимым |
| Условия сделки в момент одобрения | Снимок | Юридически значимы, изменение = новое решение |
| Текущий статус клиента в АБС | Ссылка | Источник истины снаружи, нужна актуальность |
| Справочные значения (курс, тариф) | Снимок значения и версии справочника | Пересчёт задним числом искажает историю |
| Документы | Неизменяемый файл плюс метаданные | Подписанный документ нельзя менять по определению |

Снимок — это не «копия всей базы». Снимок решения содержит ровно те поля,
которые участвовали в правиле: сумма, срок, балл и версия модели, состав
стоп-факторов, ключевые показатели отчётности, версия правил. Обычно это 15–30
полей, и хранятся они в самой записи решения.

## Два журнала, которые нельзя путать

| Признак | Журнал событий объекта | Журнал доступа |
| --- | --- | --- |
| Что фиксирует | Изменения состояния: кто, когда, что изменил | Обращения к данным: кто, когда, что просмотрел или выгрузил |
| Зачем | Восстановить историю, разобрать инцидент, показать пользователю | Расследование утечек, отчёт внутреннего аудита и ИБ |
| Содержимое | Событие, идентификаторы, старое и новое значение бизнес-полей | Идентификаторы субъекта и объекта, тип операции, результат — **без значений данных** |
| Кто читает | Пользователи, поддержка | Только ИБ и аудит |
| Срок хранения | По сроку жизни объекта | По требованиям банка, обычно дольше |

Ключевое различие в третьей строке. Журнал доступа не должен содержать сами
данные: иначе он превращается во вторую, худшую копию чувствительных сведений —
с более широким доступом и без маскирования. Записывается факт: сотрудник
такой-то открыл заявку такую-то в такое-то время и получил доступ к разделу
«кредитная история».

Оба журнала — append-only. Возможность отредактировать или удалить запись
журнала обесценивает его как доказательство.

## Удаление и сроки хранения

Требование «удалить персональные данные» конфликтует с требованием «хранить
кредитное досье». Разрешается это не выбором одного из двух, а разделением: для
каждого набора данных фиксируются основание обработки, срок хранения и действие
по его истечении.

Мягкое удаление (`deleted_at`) — способ сохранить целостность ссылок, но не
способ удалить персональные данные: данные остаются в базе, в резервных копиях и
в индексах. Настоящее удаление означает физическое удаление или необратимое
обезличивание, включая резервные копии по истечении их срока.

## Где ошибаются

- **Обновление записи решения.** Правка «на месте» уничтожает историю; решение
  отменяется новым решением, а не редактированием старого.
- **Значения персональных данных в журнале доступа.** Он живёт дольше и доступен
  шире — так утечка становится масштабнее исходной.
- **Отсутствие срока хранения у чувствительных копий.** Отчёт БКИ, полученный
  один раз, живёт в базе годами, потому что никто не назначил срок.
- **История «для отчётности», которую нельзя показать пользователю.** Если
  историю изменений заявки видит только администратор базы, поддержка продолжит
  спрашивать у разработчиков.

## На конвейере

Состав снимка в записи решения:

| Группа | Поля |
| --- | --- |
| Параметры заявки | Сумма, срок, продукт, отделение |
| Клиент | ИНН, признак группы связанных заёмщиков, дата регистрации |
| Скоринг | Балл, версия модели, дата расчёта |
| Кредитная история | Идентификатор отчёта, число действующих кредитов, максимальная просрочка за 12 месяцев |
| Проверки | Результаты ПОД/ФТ и СБ в виде «пройдено / не пройдено» и кода причины |
| Правила | `rules_version`, идентификаторы сработавших правил |
| Авторство | Сотрудник, роль, время, тип решения: автоматическое или ручное |

Сроки хранения, согласованные с комплаенсом (значения — политика банка, а не
требование закона напрямую; при переносе в свой проект уточняйте у юристов):

| Данные | Срок | По истечении |
| --- | --- | --- |
| Заявка и решения | 5 лет после закрытия сделки или отказа | Обезличивание: ПДн заменяются на хеш, статистика сохраняется |
| Отчёт БКИ, заявка одобрена | До закрытия сделки, в составе досье | Удаление файла, метаданные остаются |
| Отчёт БКИ, заявка отклонена | 30 дней с даты решения | Удаление файла, в результате проверки остаются агрегаты |
| Отчёт БКИ, согласие отозвано | Немедленно | Удаление файла, запись об удалении в журнал |
| Сканы документов клиента | 5 лет | Удаление из объектного хранилища по расписанию |
| Журнал событий заявки | 5 лет | Архив |
| Журнал доступа | 5 лет, `NFR-6` | Архив в неизменяемом хранилище |

Пример записи журнала доступа — ровно столько полей, сколько нужно ИБ:

```json
{
  "event_id": "0f7c1e7a-2b4b-4c2e-9e2a-1f5b6a0c9d31",
  "occurred_at": "2026-09-13T09:41:22Z",
  "actor_id": "emp-4821",
  "actor_role": "underwriter",
  "action": "read",
  "object_type": "application",
  "object_id": "MSB-2026-004312",
  "data_scope": ["credit_report", "pd_contacts"],
  "access_reason": "assigned_task",
  "result": "granted",
  "request_id": "b3f1c2d4"
}
```

Ни одного значения персональных данных: только `data_scope` — какие разделы были
раскрыты. Поле `access_reason` отвечает на вопрос «почему этому сотруднику это
показали»: `assigned_task` (заявка назначена), `branch_scope` (заявка своего
отделения), `investigation` (расследование СБ). Именно по этому полю ИБ ищет
аномалии — просмотры без назначенной задачи. В модуле про доступ это поле станет
основой отчёта об избыточных обращениях.
