# Сценарии и критерии приёмки

Сценарий описывает, что происходит; критерий приёмки — как проверить, что это
произошло. Разные вещи: сценарий может быть безупречным, а приёмка невозможной,
если в критериях написано «система корректно обрабатывает ошибку».

## User story или use case

Обе формы описывают поведение, но покрывают разные случаи.

| Признак | User story | Use case |
| --- | --- | --- |
| Объём | Одно действие одного актора | Цель актора целиком, с ветвлением |
| Альтернативы | В критериях приёмки | Отдельными потоками |
| Когда лучше | Понятный процесс, короткий шаг, есть с кем уточнить | Много участников, много исключений, цена ошибки высока |
| Риск | Контекст теряется между историями | Документ на 4 страницы, который не читают |

Во внутренних системах с несколькими ролями и обязательными проверками чистые
user story работают плохо: один шаг андеррайтера порождает шесть исключений, и
они расползаются по критериям приёмки разных историй. Рабочий компромисс —
use case на цель актора («принять решение по заявке») плюс user story на каждый
кусок поставки, со ссылкой на use case.

## Как писать критерии приёмки

Форма Given/When/Then задаёт три обязательные части: предусловие, действие,
проверяемый результат. Полезна не сама форма, а дисциплина, которую она
навязывает: без предусловия непонятно, в каком состоянии система, без
конкретного результата нечего проверять.

Требования к формулировке результата:

- Называет состояние, поле, код или текст — то, что видно снаружи.
- Не содержит слов «корректно», «правильно», «соответствующим образом».
- Не описывает расположение элементов интерфейса: они меняются, поведение — нет.
- Проверяется одним человеком без обращения к автору.

Негативные критерии обязательны, и их обычно больше, чем позитивных. Для каждого
шага выпишите три группы: нарушение предусловий, отказ смежной системы, попытка
действия без прав. Третья группа во внутренних системах регулярно пропускается,
а именно она чаще всего оказывается дефектом на проде: функция работает, но
работает и для того, кому не положено.

## Где ошибаются

- **Критерий описывает реализацию.** «В таблице `applications` выставляется
  `status = 3`» невозможно проверить в интерфейсе и он сломается при рефакторинге.
- **Один критерий на пять проверок.** Составной критерий даёт неопределённый
  результат: часть выполнена, часть нет — приёмка зависает.
- **Нет критериев на права доступа.** История «андеррайтер видит отчёт БКИ» без
  парного «менеджер не видит отчёт БКИ» проходит приёмку при полностью открытом
  доступе.
- **Данные в критерии выдуманы.** «Клиент с хорошей историей» непроверяемо;
  нужен конкретный набор: ИНН тестового клиента, балл 700, ноль просрочек.

## На конвейере

Use case «Отправка заявки на проверку», сокращённо до сути:

**Актор:** кредитный менеджер. **Предусловие:** заявка в статусе `draft`,
создана этим менеджером. **Результат:** заявка в статусе `checks_running`,
запущены проверки.

| Поток | Шаги |
| --- | --- |
| Основной | Менеджер заполняет ИНН → система подтягивает данные из ЕГРЮЛ → менеджер указывает сумму и срок → прикладывает согласие и финансовую отчётность → отправляет → система проверяет полноту → статус `checks_running` |
| A1. Клиент уже в портфеле банка | После ввода ИНН система находит `customer_id` и заполняет реквизиты из АБС; менеджер не редактирует эти поля |
| A2. Сумма выше лимита полномочий отделения | После отправки заявка дополнительно помечается признаком `committee_required` |
| E1. ЕГРЮЛ недоступен | Поля заполняются вручную, заявка помечается `egrul_unverified`, проверка повторяется автоматически в фоне |
| E2. Нет файла согласия | Отправка отклоняется, ошибка `consent_required` |
| E3. Клиент в стоп-листе СБ | Заявка отправляется, но сразу уходит в `manual_review` на сотрудника СБ; менеджер причины не видит |

Поток E3 — пример требования, которое нельзя придумать за столом. Его
формулировку дала служба безопасности: менеджеру нельзя показывать, что клиент в
стоп-листе, иначе информация уходит клиенту. В критериях приёмки это выглядит
так:

```gherkin
Дано: клиент с ИНН 7701234567 включён в стоп-лист СБ
И менеджер Петров работает в отделении М-12
Когда Петров отправляет заявку по этому клиенту
Тогда заявка переходит в статус manual_review
И в очереди сотрудника СБ появляется задача с типом stop_list_check
И в карточке заявки Петров видит статус "На проверке"
И карточка заявки не содержит признака стоп-листа ни в одном поле,
   ни в ответе API GET /applications/{id}
```

Последняя строка — не придирка. Без неё разработчик честно скроет признак в
интерфейсе, оставив его в JSON-ответе, и любой пользователь с инструментами
разработчика в браузере увидит то, что видеть не должен.

Негативные критерии к этой же истории, по трём группам:

| Группа | Критерий | Ожидаемое поведение |
| --- | --- | --- |
| Предусловие | Отправка заявки в статусе `submitted` | `409 Conflict`, код `invalid_state`, статус не меняется |
| Смежная система | ЕГРЮЛ отвечает дольше 5 с | Заявка уходит с пометкой `egrul_unverified`, фоновая повторная попытка через 15 минут, до 3 раз |
| Права | Менеджер отделения М-12 открывает заявку отделения М-07 | `403 Forbidden`, событие в журнале доступа, заявка не отображается в списке |
| Права | Андеррайтер меняет сумму в заявке | Поле недоступно на запись, `403 Forbidden` при прямом запросе |
| Права | Менеджер, создавший заявку, принимает по ней решение | Действие недоступно: правило сегрегации обязанностей |

Последняя строка — критерий, вырастающий из бизнес-правила «четырёх глаз»: тот,
кто готовит заявку, не принимает по ней решение. Само правило живёт не здесь, а
в каталоге правил — этому посвящён следующий урок.
